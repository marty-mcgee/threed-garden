# v0.34.0 - App: Home and Guest Landing Pages

## Plan and status

November 14, 2026: the Developer agreed to the proposed direction and requested this planning checkpoint as `plans: docs: v0.34.0`. Start with the App Home page, then use its accepted presentation to guide other outer/upper-level landing pages. This request records the plan; no implementation, version bump or release preparation has occurred.

Observed baseline: main / `24fdb70deae03913a8223b4fcc2bfa3e6634487f`, package and both root lockfile versions 0.33.2. Existing AGENTS, CONTEXT and v0.33.2 production-confirmation edits are preserved. This record is the single home for v0.34.0 scope, future checks, acceptance and release evidence.

## Goal

Make landing pages more attractive, useful and appealing to Guest Users visiting in browsers. Home should quickly explain what ThreeD App offers, show a compelling real example, and make the next action obvious. Retain the garden character, existing App branding, dark/light themes and working public experiences.

## Current observations

Source review covered `src/app/page.tsx`, `src/components/home/GardenHero.tsx`, `src/components/home/WhyThreeDApp.tsx` and the shared App header. This was not a rendered-browser visual audit; the public web reader returned no readable Home content.

- The interactive garden, green palette, generous buttons and theme support provide a useful foundation.
- The hero gives similar prominence to the garden, Traffic, music and GitHub, then repeats those destinations below. Tech Stack appears before the feature cards.
- The hero is an illustrative garden layout, not a capture of the full App workspace.
- Home returns no content until its client mount completes.
- The garden action targets Project 17, while the preview's Scene link has no Project identity. Guest availability must be verified before choosing a consistent demo destination.
- Several Home fetch/playback failures only reach the console. The hero badge opens Home again in a new tab.

## Agreed presentation direction

1. Give the hero one primary **Explore a Demo** action and a secondary **Learn ThreeD** action. Move other destinations into the following section.
2. Pair the interactive garden with a strong actual App capture showing linked Design/3D views. Clearly distinguish the illustrative preview from the working App.
3. Present **ThreeD, Multimedia, Traffic and Learn** as four peer destinations using existing Module icons/colors and short visitor-focused descriptions. Use Multimedia consistently as the Module name; music describes an experience within it.
4. Add a small showcase of real public Projects with actual captures, short captions and **Open Project** actions. Garden, architecture and an interactive Scene are candidate subjects, not claims of currently verified Guest access.
5. Explain what Guests can view or try and when an account is needed beside the relevant actions. Verify the existing access contract; do not broaden permissions or promise Guest saving.
6. Move technical details and GitHub into a compact developer section near the bottom, retaining the open-source identity.

Suggested hero copy, to refine in the presentation review:

> **Plan your space. Build your world.**
>
> Explore garden layouts, architectural ideas and interactive Scenes in ThreeD App.
>
> **Explore a Demo** · **Learn ThreeD**

This is supporting copy, not a rename of the App.

## Proposed Home sequence

1. Hero: clear promise, two actions and a compelling preview.
2. Explore the App: four peer Top Module cards.
3. See what you can create: real public Project examples.
4. Start exploring: choose an example, explore its views, follow a guide.
5. Featured Multimedia: preserve playback, introduce it clearly and place it deliberately.
6. Common questions: Guest access, saving Projects, browser/device requirements and open-source availability. Answers must reflect verified current behavior.
7. Final invitation and footer: repeat the primary action and retain Learn, sign-in and developer links.

Use fewer competing bordered panels, clearer headline/body/caption hierarchy, larger real screenshots and restrained Module color accents. Preserve both themes. Clear content and imagery take priority over additional animation.

## Implementation phases

### Phase 1 - Home hierarchy and Guest guidance

- Refine the hero, actions, four Module cards and section order.
- Preserve established names and shared styling owners; avoid changing Admin navigation or personal preferences.
- Remove the redundant new-tab Home link.
- Verify existing Guest destinations and make the demo actions consistent.
- Review desktop/mobile presentation and both themes before expanding to other pages.

### Phase 2 - Actual App showcase and first-use experience

- Select verified public Projects and capture their actual App screens with accurate captions and purpose-based filenames. No private content or invented product screenshots.
- Retain the interactive garden and its fallback/reduced-motion handling; clearly label illustrative content.
- Make the introduction and navigation available while interactive features initialize, replacing the whole-page mount gate with appropriately scoped client behavior.
- Add visible Multimedia loading/error/retry feedback through existing playback and authorization boundaries. Preserve intentional playback without autoplay surprises.
- Add the short getting-started sequence and factual common questions.

### Phase 3 - Extend the accepted landing-page approach

- Review candidate upper-level ThreeD, Multimedia, Traffic and Learn entry pages individually against their current purpose and Guest access.
- Reuse the accepted typography, action hierarchy, spacing, imagery and Guest guidance where appropriate. Do not impose one layout on distinct browsing experiences.
- Define each page's concrete scope before implementation. No new routes, schema or content-management system are prerequisites.
- For Learn or README work, follow the [Learn Art Image Development Requirement](../developers/LEARN_ART_IMAGE_REQUIREMENT.md), preserving database content authority and actual-screen documentation.

## Boundaries

Follow the established [Schema-First, Top-Down Module architecture](../plans/app-module-architecture.md). ThreeD, Multimedia, Traffic and Learn remain peer Top Modules; landing-page presentation does not redefine ownership.

Preserve public/private authorization, existing Project Save/load, the single persistent Project Canvas/Rapier world, Character behavior, Terrain editing and both Save controls. No schema, dependency, live database or device changes are proposed. Keep Developer servers and active dependencies untouched. Staging, commits, pushes and deployment require their existing explicit authorization.

## Acceptance and validation plan

- A first-time Guest can identify the App's purpose and primary next action without opening menus.
- Demo, Module, Project, Learn and account links resolve to the intended current destinations; Guest limitations are accurately stated.
- Actual screenshots and illustrative content are clearly distinguished. Showcase content is verified public.
- Desktop and narrow layouts work in both themes without clipped text, horizontal overflow or obscured actions. Keyboard focus, readable contrast, meaningful image alternatives, touch targets and reduced-motion behavior remain usable.
- Introductory content and navigation do not depend on the interactive preview becoming ready. Preview failure leaves a useful fallback.
- Multimedia retains existing playback behavior and public scope, with visible loading, empty, error and retry states.
- Run relevant focused offline checks and fresh TypeScript after implementation; run applicable CI and a guarded isolated build during release preparation. Keep mocked results, actual browser observations, Developer acceptance and production confirmation distinct.
