## Implementation and acceptance criteria

- Optional `appearance.elevationColors` stores Sea Level in metres, Water color and six ordered bands with start thresholds in metres above Sea Level. Shore starts at zero; Water includes Sea Level. Invalid colors, non-finite/out-of-range numbers, unordered thresholds, unexpected fields and incomplete band lists are rejected by the shared parser before persistence.
- Existing Terrains remain single-colored until enabled. At the Developer's request, the complete Colors and thresholds form stays visible while inactive; its fields are disabled and explanatory text identifies the current Surface color mode. The editor preview and Project Scene use the same elevation-color selection and linear-space vertex colors. Bands blend across grid triangles. Mountains, hills and valleys retain the existing generator, sculpt and drawing controls.
- Sea Level is a color threshold, not a new flat water surface or water-physics system. Heights, borders, placement, collision geometry, spawn sampling and the persistent Canvas/Rapier owner are unchanged.
- Apply colors and thresholds commits one existing Undo/Redo step. Both Save controls are disabled while a color draft awaits Apply. Invalid drafts remain editable. Generation retains the palette and existing drawing operations. Both Save controls use the existing authenticated revision API; existing Project placements remain pinned to their selected revision.
- No SQL migration, dependency change, live database operation or reference-app runtime dependency. No server was started or stopped.

## Individual band switches

A disabled land band falls back to the highest enabled band below that elevation, or the Terrain's Surface color if none applies. Disabled Water uses Surface color. All seven off uses Surface color everywhere, without altering geometry. The existing global enable control is retained.

## Browser acceptance

1. Open an owned Terrain under `/admin/threed/terrains`. Confirm its existing single color and drawings are unchanged, and all color/threshold fields are visible but disabled. Enable **Colors and thresholds > Elevation colors**.
2. Edit Sea Level and the band colors/start thresholds, then **Apply colors and thresholds**. Expect the preview to recolor without changing its shape. Use low thresholds for a low-relief Terrain; the displayed height range helps choose them.
3. Enter a threshold below its predecessor or clear a numeric field. Apply must show an error, retain the inputs and leave both Save controls disabled. Correct the input and Apply; Undo/Redo should restore the previous/applied palette as one step.
4. Generate with the same seed/settings and test a sculpt/drawing edit. Expect the palette to remain, deterministic base generation and existing editable drawings/Undo/Redo to work.
5. Save using each existing Save control on separate edits, then reopen. Expect the selected colors/thresholds to persist. Disable elevation colors and Save/reopen to restore the single-color appearance.
6. Explicitly select the new Terrain revision in a test Project and Save. Expect the Scene palette to match the editor, with unchanged ground contact and placement. Other Projects pinned to earlier revisions must remain unchanged.

## Rollback and release boundary

Older revisions remain immutable; pre-feature App code rejects the optional field, so rolling code back requires selecting pre-feature revisions for affected Projects or retaining the compatible parser. Do not delete or rewrite saved revisions as a rollback shortcut.

## Manual camera-view saving

The Developer requested Terrain camera changes participate in saving, then explicitly selected **Enable Save Changes; save manually** rather than autosave. Optional appearance.previewCamera stores the editor's perspective camera position, orbit target, zoom and field of view in the existing Terrain revision JSON. Runtime clipping distance is derived and is not stored. Earlier revisions without a camera retain their default view. No table migration or separate API/save path is introduced.

User orbit, pan and zoom changes mark the draft dirty and enable both Save controls. Restoring a view does not mark it dirty. Camera state is tracked separately from geometry/history, so damping updates do not rebuild the mesh or add Terrain sculpt Undo steps. Manual Save captures the camera alongside the current Terrain draft; only successful Save acknowledges it. Failed or conflicting saves retain the draft. Reopening restores the saved position, target and perspective settings. Existing Project Scene cameras remain unchanged; this does not introduce a named Views library or an orthographic mode.

Fresh isolated TypeScript and focused checks pass for bounded camera parsing, legacy compatibility, round-trip, actual control restoration/hydration guard/user-movement capture, and the actual Save function's request payload and success-only camera acknowledgment. Persistence and controls are mocked in these checks. All 110 guarded offline CI tasks passed after this camera-persistence change; the final focused actual Save-payload regression also passed. Browser acceptance: reopen a Terrain (Save should start disabled), orbit/pan/zoom (both Save controls should enable), Save with either control and reopen to verify the view. Failed Save must retain unsaved view status. No live database operation or autosave was performed.
