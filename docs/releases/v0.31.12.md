#### November 9: missing upload-length header

The Developer's first App import attempt failed with HTTP 400, `Missing
[x]-content-length header.` The shared Model uploader forced multipart for every
file. An offline regression using the installed Blob SDK 2.4.0 reproduces that
rejection on its bodyless multipart-create request, which omits the length header;
the actual App helper fails against that boundary before the fix.

The bounded 32 MiB Model path now uses a single direct PUT. The same installed-SDK
regression passes after the correction and verifies that the transmitted byte
count equals `x-content-length`, followed by the existing completion verification.
Signed authorization, ownership, file limits and failed-verification cleanup are
retained. Fresh TypeScript, Model upload, JSON Assembly and existing Assembly
import checks pass with mocked storage/API boundaries; documentation and whitespace
checks pass. The earlier 108-task CI result predates this fix;
actual App retry acceptance remains pending.

#### November 9: completion metadata diagnosis

The Developer's next attempt reached completion but returned the combined
`Uploaded Model metadata could not be verified` error. That response does not

All eight focused direct-upload groups and the installed SDK transport regression

The Developer then reported an expected 1,820 bytes versus zero from provider

and still requires its exact signed byte count and valid GLB contents. The next
Developer response confirmed **the stored body itself contained zero bytes**;

Small primary Files up to the existing 4 MiB server-transfer budget now use the

transports still run the signed stored-byte completion check. The browser SDK

verifies the actual App helper supplies the exact original bytes as a File and
