# v0.38.0 Project Save As: New Version

On November 25, 2026, Marty approved implementing Project duplication first. The Scene's Project menu and toolbar now offer **Save As: New Version** to the signed-in owner.

## User workflow

1. In Project 18, move a wall, then choose **Save As: New Version** beside **Save Project**. Enter an editable Project name such as **Marty's Project 18 v001**.
2. Capture the current Scene and Design draft at confirmation. Create a private Project owned by the signed-in source owner, with a fresh ID and slug. The name is the User's choice, including the version suffix.
3. Open the new Project after creation is confirmed. It contains the moved wall. Future **Save Project** actions target the new ID. Reopening the saved original shows the wall at its previous location.
4. Canceling or failing preserves the current editor and draft. If a separate editor prevents switching, or more edits were made after capture, keep the current editor open and offer **Open created Project**. A retry after a lost response must recover the same Project.

## What the copy owns

| Content | Behavior when duplicating a Project |
| --- | --- |
| Project and workspace | Copy details, featured image reference, setup, units, calibration, supported configuration and metadata, Design geometry and Levels, named views, camera, visible overlays, reference Media selection and viewer placement. Use the existing explicit Save capture for current positions and edits. Preserve setup-only Projects when duplicating saved data. |
| ThreeD records | Create independent marker placements, ThreeD Groups and memberships, Terrain placement, Ground Map assignment and alignment, and Scenario and Simulation definitions. Rebuild the destination's current Design projection from its architecture. Preserve any other Project-associated Design records as separate records with fresh create keys. |
| Module and asset assignments | Copy the ThreeD, Multimedia and Traffic Project assignments, their per-Project settings, Project Assets, direct reference Media and Lyrics assignments, including inactive memberships. Preserve reusable catalog IDs for Models, Textures, Characters, Media, Albums and Terrain revisions. Each Project can move placements or remove assignments independently. Learn has no Project assignment table. |
| Shared files and Modules | Give each Project independent Ground Map settings and share the backing image safely. Where a ThreeD Module is owned through a legacy Project foreign key that cascades on deletion, give the version an independent Module record and remap its dependents. Keep reusable saved Module instances linked through their ordinary assignments. |
| Activity | Keep Simulation Results, playback history and FarmBot command and device history with their original owners. Copy authored sensor configuration and bindings. Start runtime counters and occupancy fresh in the new Project. Opening a version must never dispatch a command or start a Simulation. |

The [Project schema](../../src/libraries/schema/project/index.ts), [ThreeD schema](../../src/libraries/schema/threed/index.ts) and [Multimedia schema](../../src/libraries/schema/multimedia/index.ts) distinguish an assignment, an editable Project record and a reusable asset. For example, changing a placed Model's position belongs to its Project. Editing the underlying library Model is a shared catalog edit.

The copy rechecks access to assigned assets. An unavailable asset on an attached Module produces a conflict so the owner can review the source. Inactive Module assignments remain eligible. Historical Layer and Weather Log links can follow their owner, while stale asset rows from detached Modules stay with the source. Runtime Marker placements come from the Project's marker records.

## Reusing Save As for other records

Project is the first implementation. A User duplicating a Project gets independent placements of the same catalog assets. A future **Duplicate** action on a Model, Character or Terrain would create a catalog record the User could edit and assign separately. For example, duplicating a Character would let Marty change its movement speed while existing Projects continue using the original Character.

The common workflow identifies the source, asks for a name, verifies ownership, creates one destination per confirmed request and returns its ID. Each editor should say whether it is copying a saved record, a selected revision or the current editable draft. The request key covers the kind of record, source and submitted content so a retry can recover the same result. Each owning service defines its own transaction, editable fields, access defaults, related records and ID mappings. Project lineage and Terrain revision numbers belong to their respective owners. Additional types can adopt the workflow as their copy rules are agreed.

| Future action | Independently editable in the copy | Reused or retained |
| --- | --- | --- |
| Duplicate Model | A new Model with its own geometry-source settings, File attachment records, Category, material, Animation and Album assignments. Remap the primary File to the copied attachment and preserve bundle paths and load order. | Reuse authorized catalog Categories, Textures, Animation clips and Albums. Shared file bytes require replacement and deletion checks for both Models. Existing placements and Characters keep their original Model ID. [Model API](../../src/app/api/threed/models/route.ts) |
| Duplicate Character | A new Character with a fresh database ID and unique Character identifier, its own movement, interaction and appearance settings, Model links, Album links and explicit Animation overrides. Keep inherited and disabled Actions distinct. | Reuse the referenced Models, Animation clips and Albums. Existing Project placements keep their original Character. [Character schema](../../src/libraries/schema/threed/index.ts), [Character Albums](../../src/app/api/threed/characters/[id]/albums/route.ts) |
| Duplicate Terrain | A new Terrain whose revision 1 captures the chosen source revision's dimensions, sculpted heights and appearance. Subsequent saves advance the new Terrain's own revisions. | Existing Projects keep their Terrain ID, pinned revision and placement. Duplicating an entire Project instead gives it its own placement of that pinned revision. [Terrain API](../../src/app/api/threed/terrains/route.ts) |

For each future action, exercise a named copy, edit it, reopen the original, and retry the same request after a lost response. Check that existing Project placements still resolve, that removing either copy respects resource lifetimes, and that inaccessible source records cannot be copied. These object actions are future candidates. The v0.38.0 implementation scope in this plan is Project Save As.

## Implementation

1. **Capture the draft.** Extract the capture used by [Save Project](../../src/app/dashboard/scene/SceneWorkspace.tsx). Include pending Model positions, Group edits, Design v13, Terrain and workspace state. Separate capture from the acknowledgement that clears saved edits. Retain loading, busy and independent editor guards. Only the Scene can supply an in-memory draft. A future Admin entry point would have to identify its source as the last saved Project.
2. **Prepare persistence.** A nullable source Project link becomes null when the original is deleted. An owner-scoped unique request key binds the source and submitted content to the resulting Project. Existing Projects require no parent. Each Project owns its Ground Map assignment and alignment. The [Ground Map API](../../src/app/api/threed/ground-maps/route.ts) checks for remaining references before deleting the stored image after replacement or removal.
3. **Copy in one transaction.** Add an owner-only Project creation operation. Read a consistent source, validate the draft with the same bounds, reference checks and conflict guards as [Save Project](../../src/app/api/project/threed-markers/route.ts), then insert the destination and its dependent records. Preserve server-owned fields through typed mappings. Assign new database IDs and remap Ground Map, Terrain placement, Scenario, Simulation, marker-row and inspector references. Preserve Design entity IDs and runtime marker keys where they are scoped to the Project. Reject unsupported or inconsistent references with an actionable error and roll back the entire copy.
4. **Connect the Scene action.** Validate the name, show which Project is being copied and confirm the new name and ID from the server. Handle a double-click, timeout retry and navigation veto. Reuse the [Project menu](../../src/components/map/header/ProjectHeaderMenu.tsx) and existing Project-switch behavior.

## Rollout and verification

The Developer applies the [Project duplication migration](sql/project-duplication.sql) before running the updated App against that database. Begin using Save As once every serving instance runs the updated code. During a rolling deployment, an older instance could still delete a shared Ground Map image or retire a Bed or Planting placed in both Projects.

The [Project duplication check](../../src/libraries/scripts/validate-project-duplication.cjs) runs the POST handler and Drizzle queries against an in-memory SQLite fixture. Coverage includes a moved wall and Model, Stairs, Group membership, reference Media, a pinned Terrain revision, Ground Map and Scenario Album links, source deletion, stale or unauthorized requests, transaction rollback and retry after a lost commit response. Separate checks exercise the dialog, reference remapping and returning to the original Project's saved wall position in the same Scene session. A retry retains its original request in memory while the Scene is open.

The [Ground Map storage check](../../src/libraries/scripts/validate-ground-map-storage.cjs) exercises image replacement and deletion with mocked storage. The [Bed and Planting removal check](../../src/libraries/scripts/validate-project-garden-placement-removal.cjs) exercises both removal orders and checks that a remaining placement, inactive assignment or dependent garden record keeps its catalog asset.
