## ThreeD App nomenclature for v0.32.x

Reaffirmed November 9, 2026, after rereading [README](../../README.md),
[CONTEXT](../../CONTEXT.md) and [AGENTS](../../AGENTS.md), using the established
[Schema-First, Top-Down architecture](../plans/app-module-architecture.md).
These names describe the existing App, not a replacement architecture.

| Term | Established meaning and usage |
| --- | --- |
| **ThreeD App** | The application/product name. |
| **ThreeD Garden** | The repository name and existing deployment identity; preserve named Projects and existing labels in their own contexts. |
| **Top Modules** | Exactly four peers: **ThreeD, Multimedia, Traffic and Learn**. |
| **Admin surface** | The application surface for authorized CRUD, configuration and management. Being displayed here does not establish ownership by a Top Module. |
| **Dashboard surface** | The front-end surface for Project workspaces, Scene/maps and supported discovery/playback. A route or mount location does not establish domain ownership. |
| **Saved Module instance** | A persisted Module configuration/collection where the existing schema defines one. Its identity is separate from a content record. |
| **Sub-module** | A type within its owning Top Module, such as Models within ThreeD or Albums within Multimedia. |
| **Record** | A particular saved entity with its actual schema identity, such as one Model or Album. |
| **Project** | The workspace boundary for assigned content, placements, architecture and explicit Project Save/load. A Project assignment is distinct from a reusable catalog relationship. |
| **Scene instance** | A particular placement in a Project with its own runtime marker identity; it is distinct from the source Model record. |
| **DetailsCard** | Keep this exact name and its Developer-established contextual hierarchy: **ThreeD > Project > Model > DetailsCard**. |
| **App Settings** | Shared App-wide configuration managed by authorized Super Admins. Keep this scope distinct from personal workspace preferences and browser-local presentation. |
| **Personal workspace preferences** | Account/browser-scoped choices using their existing owners and persistence. They are not global App Settings. |

## Ownership and HTML output

- Existing `settings` and `settings_audit_logs` store one system JSON definition,
  `app.meta-tags.v1`; no schema/migration is introduced and no live writes were run.
- The save transaction rechecks the active, non-deleted Super Admin, locks the
  definition and compares revisions. Concurrent/stale writes reject; audit
  failures roll back the update. Failed saves retain the client draft.
- Root `generateMetadata` maps saved tags through Next's Metadata API. Values
  become escaped metadata, not raw injected HTML. Disabled/missing settings
  preserve the existing description. Settings outages use that same fallback
  without blocking the page or overwriting stored values.
- App-wide metadata supplies defaults. Existing child-route metadata retains
  Next inheritance/override precedence. Existing AppPageTitle remains the title
  owner. The Project-specific stage below supplies permitted overrides for the
  canonical Scene URL. Crawler directives do not grant access or implement privacy.

Implementation uses the official [Next metadata contract](https://nextjs.org/docs/app/api-reference/functions/generate-metadata).
The App config disables metadata streaming for all user agents, resolving these
values into the initial document head. The response waits for the Settings read.
This is not browser-only DOM injection or a standalone HTML exporter.
