# v0.22.10 — ThreeD Playable Soccer

**Draft plan, September 29, 2026.** The User selected Character actions and ball interaction as the next priority. This document proposes implementation scope; no runtime changes or release preparation have occurred. Production remains v0.22.9, release commit `fcbab81c`; the inspected checkout is `dc6e42d2` with an initially clean worktree.

## Outcome and recommended scope

In Project 15, take control of an eligible Character, select a particular movable ball as the Action Target, approach it with WASD, and trigger one supported mapped kick. After the one-shot animation completes, that ball receives one bounded physical impulse through its existing Rapier owner. Moving it into an existing goal sensor increments the existing session counter once per entry.

Start with Farmer Kate and one verified foot-kick mapping. Use the same capability for other eligible Characters, but do not make Joey, Scarecrow, headers, passes, penalties, teams, or match rules prerequisites for this release. Their asset preparation and rig compatibility are separate follow-ups. No automatic Character placement or live catalog edits are included.

- `src/components/map/ThreeDScene.tsx` owns Model rigid bodies, live position reporting, dynamic ball colliders, and sensor callbacks. Ball movement must remain here, through the existing body owner, rather than through mesh transforms or a second physics world.

The [earlier Soccer investigation](v0.22.4-physics-soccer.md) recorded Kate, existing Soccer mappings, and multiple ball instances in Project 15. Treat those catalog observations as historical until checked again. Do not assume a clip label establishes a usable semantic mapping or compatible rig.

## Implementation checkpoints

### 1. Establish the browser baseline and action contract

Inspect the actual action-menu builder, semantic mapping resolution, completion payload, Model instance identity, live body position, and sensor event path before editing them. In Project 15, verify Kate's mapped clip, ball/field collider alignment, contact movement, and goal entry/exit. Record exact marker identities, supported action key, and any reproducible failure. Correct only a proven blocking physics defect in a separate step.

Define a bounded client-only interaction request containing Project/session identity, actor instance, target ball instance, semantic action, and unique request ID. A request must not be authorized by a reusable Model ID or stored coordinates alone. Choose finite range, elevation, impulse, and speed limits from current Scene units, effective ball radius/mass, and browser evidence; record the selected values before implementation.

Acceptance: a documented working contact baseline and one verified Kate kick mapping, plus an exact-instance contract and measurable limits. No assumption that Start Scenario certifies playability.

### 2. Add targeted kick eligibility and lifecycle

Expose the verified mapped kick only for a controlled movable Character and an active, visible, dynamic movable-ball target in the same Project. Require current runtime positions and a loaded compatible mapping. Explain unavailable mapping, missing control, out-of-range, and busy states. Ordinary Model targets retain generic interactions.

Use manual WASD approach for the initial scope. Reuse the established facing/task path where suitable. Correlate completion with the pending request; do not accept a generic animation-complete event as permission to move an arbitrary ball.

Acceptance: only the intended actor and ball are eligible; repeated clicks cannot start overlapping requests. Release Control, Project switch, actor/target removal, Layer hiding, target replacement, or missing-completion timeout cancels the request. Cancelled, duplicate, late, and mismatched completions do nothing. Locomotion and controls recover normally.

### 3. Apply one physical effect after completion

Add the smallest typed handoff to the existing ball body owner. Recheck Project/session, exact actor/ball identity, visibility, body availability, current range, and request state immediately before consuming it. Compute a finite direction from the live actor toward the live ball; reject coincident/invalid positions. Use one bounded ground kick initially, with no aim/power editor. Bound resulting motion so repeated kicks cannot accumulate unlimited speed.

Only the ball owner applies the impulse at a safe physics update boundary. Consume each request at most once, even across duplicate completion delivery. A ball that rolls out of reach during the animation receives no remote kick; show useful cancellation feedback.

**Timing constraint:** root AGENTS.md requires world actions after one-shot completion. This plan therefore does not apply an impulse at a foot-contact frame. Verify whether that delay feels acceptable with the chosen clip. If it does not, record the result and propose a separately reviewed timing-boundary change rather than silently breaking the rule.

Acceptance: one completed request moves exactly one selected ball; another instance of the same reusable Model receives no kick effect. Mesh and collider stay aligned, and unrelated owners remain mounted. Report effect success only after the body owner accepts the effect, not merely after animation completion.

### 4. Complete the Soccer journey and release review

Update Soccer guidance with the verified control → target → approach → kick → observe-count flow. Distinguish setup checks, action availability, animation completion, and observed sensor entry. Keep generic Sensor counters as the sole counting authority; no synthetic goal increment from the kick handler. Preserve existing session-wide Reset All Counts semantics and Project Save behavior.

Acceptance: Kate can complete that journey in Project 15, goal entry counts once, remaining inside does not repeat, and exit/re-entry counts again. Two balls from the same Model count independently. Project switching and reload preserve the existing saved setup contract and never replay a pending kick. Counts remain session-only.
