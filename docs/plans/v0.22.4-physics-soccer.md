## Code-path findings that shape the example

- `ProjectModelMarkerBody` mounts the three balls as dynamic Rapier bodies only after their model bounds settle, using a `BallCollider` and each instance's saved ball settings. The field requests a fixed triangle-surface collider. Sensor cuboids mount under the field body and send entry/exit observations to the generic session counter reducer. This gives one physical path to improve, rather than a second Soccer engine.
- Two Project ball markers share reusable Model 53. The current ball `userData.threeDPhysics.identity`, Physics Event source, contact tracker key, and counter occupancy key use `models:53` for both. Their separate Project marker IDs are not preserved in that event path. Simultaneous or overlapping sensor entries can therefore be conflated. The runtime position resolver also uses module type plus source asset ID, while `ThreeDActionTarget` already carries a marker ID. A kick must resolve the selected **Project instance**, not simply Model 53.
- The existing Left/Right Kick, Penalty Kick, and Header Action Slots are custom actions. In `DetailsCard`, custom action clicks currently dispatch `garden-character-action` with `target: null`, even when a Model is selected as Action Target. EcctrlCharacter can carry a target through its one-shot completion event, but the page treats all non-farming completions as animation-only. There is no current handoff from a completed kick to the ball's Rapier owner.
- The live Scene's `sensor-counter-core` is the counting authority. The historical `soccer-physics-core` is retained for compatibility validation. Changing only that historical reducer would not fix Project 15's live counters.

## Next ThreeD Physics direction

Treat Physics as **objects in groups**. Each object may participate in contact as a collider, cause a collision through motion, or receive a collision. A Sensor is a separate observation boundary: on a qualifying entry it increments a count and identifies the source object or objects involved. The count and source identity should stay generic; Soccer goals are one Project example, not the Physics vocabulary or a separate scoring authority. Define the group membership and collision/observation rules from the existing ThreeD ownership model before adding further schema or behavior.

## Boundaries

Preserve `isMovable` routing between EcctrlCharacter and GardenCharacter, one persistent Canvas/Rapier world, generic Physics Sensor ownership, and Project-instance transforms. Do not add further schema, automatic score persistence, a parallel Soccer runtime, FarmBot commands, MQTT behavior, or unapproved world persistence. Reusable Model action mappings do not by themselves prove a Character instance can play an action; verify each named Character separately.

Focused checks include `npm run validate -- threed-sensors threed-physics-events threed-soccer-physics threed-scenarios threed-runtime-markers threed-orchestration`, plus the existing movable-object contact, reposition, environment-surface, hidden-collision, Character teleport, and assignment checks when their paths change.
