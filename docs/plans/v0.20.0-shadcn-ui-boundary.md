# v0.20.0 — shadcn/ui Component Boundary

**Status:** Implemented and validated on September 21, 2026.

## Goal

Make the repository's existing shadcn/ui component layer the explicit UI design boundary while removing the current mix of direct `@radix-ui/react-*` packages and unified `radix-ui` imports.

The target is one consistent ownership rule:

- Feature and page code imports components from `@/components/ui/*`.
- Only `src/components/ui/*` may depend on the underlying primitive library.
- The primitive dependency is the unified `radix-ui` package.
- ThreeD Blueprint styling and existing component APIs remain application-owned.

## Proven Current State

- `components.json` already configures shadcn/ui with the New York style, CSS variables, `src/app/globals.css`, and the `@/components/ui` alias.
- Product code already consumes the local shadcn-style component layer. The repository currently contains 524 `@/components/ui/*` import references.
- Direct primitive imports are isolated to 12 files under `src/components/ui`.
- Eight wrappers already use unified `radix-ui` imports.
- Four wrappers still import individual packages:
  - `label.tsx`
  - `progress.tsx`
  - `slider.tsx`
  - `switch.tsx`
- `package.json` directly declares both `radix-ui` and 11 individual `@radix-ui/react-*` packages.
- Some `@radix-ui/*` entries will remain transitively in the lockfile through dependencies such as Leva. The cleanup criterion is therefore the direct application dependency boundary, rather than an empty Radix lockfile search.

## Important shadcn/ui Model

shadcn/ui is source code owned by this repository, not a runtime component package imported as `shadcn/ui`. Its CLI copies and updates component source under `src/components/ui`; Radix supplies behavior for the Radix-backed variants.

The official `shadcn migrate radix` command converts individual `@radix-ui/react-*` imports to the unified `radix-ui` package. It does not remove Radix or convert components to a different primitive system.

## Recommended Architecture

Retain Radix as the implementation detail behind the local shadcn/ui wrappers and standardize it as one direct dependency:

```text
pages and feature components
          │
          ▼
  @/components/ui/*
          │
          ▼
       radix-ui
```

This preserves the existing behavior, accessibility contracts, component props, and ThreeD Blueprint styles while simplifying dependency ownership.

Migrating to Base UI would be a separate project. It could remove the direct Radix implementation, but it would require behavioral and API review across dialogs, menus, selects, sliders, switches, tabs, focus management, portals, and keyboard interaction.

## Staged Implementation

### Stage 1 — Freeze the component contract

Before editing:

- Record exports and public props for the affected UI wrappers.
- Confirm no product code imports `radix-ui` or `@radix-ui/*` directly.
- Capture the package and lockfile baseline.
- Define a manual interaction matrix for the primitive-backed components.

Acceptance criteria:

- The migration scope is limited to `src/components/ui` and dependency metadata.
- Existing ThreeD Blueprint CSS and component APIs are identified as preserved behavior.

### Stage 2 — Consolidate primitive imports

- Preview the official Radix migration against `src/components/ui/**` using CLI inspection or diff options.
- Convert the four remaining individual primitive imports to unified `radix-ui` imports.
- Review every change before accepting it.
- Do not use an overwrite operation or regenerate customized wrappers wholesale.

Acceptance criteria:

- No source file imports `@radix-ui/react-*`.
- Primitive imports remain confined to `src/components/ui`.
- Component exports, props, classes, and Blueprint styling remain unchanged.

### Stage 3 — Clean dependency declarations

- Remove the individual `@radix-ui/react-*` entries from `package.json`.
- Keep `radix-ui` as the single direct primitive dependency.
- Refresh `bun.lock` with the repository package manager.
- Inspect the lockfile changes for unrelated upgrades.

Acceptance criteria:

- `package.json` has no direct `@radix-ui/*` dependencies.
- `radix-ui` remains explicitly declared.
- The lockfile contains only expected resolution changes.

### Stage 4 — Enforce the boundary

Add a UI dependency check to the consolidated validation dispatcher. It should fail when:

- Code outside `src/components/ui` directly imports `radix-ui` or `@radix-ui/*`.
- `package.json` declares a direct `@radix-ui/*` dependency.
- Required shadcn aliases or the configured global CSS path drift from `components.json`.

Register the task in the normal `all` and `ci` validation profiles.

Acceptance criteria:

- New feature code must consume `@/components/ui/*`.
- The boundary is machine-checked rather than maintained only by convention.

### Stage 5 — Validate behavior

Run the relevant repository validation ladder and manually verify:

- Dialog focus trapping, Escape handling, and portals.
- Dropdown keyboard navigation and focus restoration.
- Select opening, selection, and keyboard controls.
- Slider pointer and keyboard input.
- Switch state changes and labels.
- Tabs keyboard navigation.
- Scroll areas.
- `asChild` composition in Button and Badge.
- ThreeD DetailsCards, Project Toolbar menus, Project Tour, and Admin workspaces.
- Touch behavior, reduced motion, and forced colors.

Acceptance criteria:

- TypeScript and the UI dependency validation pass.
- No visual or interaction regressions are found in the smoke matrix.
- No database schema change is required.

### Stage 6 — Document UI ownership

Document these durable rules in the agent-safe UI guidance:

- `src/components/ui` is the application-owned shadcn/ui design layer.
- Feature code imports UI components through that layer.
- Primitive imports stay private to that layer.
- Blueprint tokens and shared surface behavior belong in the local wrappers and `globals.css`.
- CLI component updates require a reviewed diff and must not overwrite local customization without an explicit migration plan.

## Release Boundary

This work is a dependency and ownership cleanup for v0.20.0. It does not authorize:

- A visual redesign.
- Component API changes.
- A Base UI migration.
- Bulk regeneration of local UI components.
- Database or schema changes.
- Unrelated package upgrades.

## Rollback

The stages are intentionally separable. If behavioral validation fails, restore the prior wrapper imports and package declarations together. No data migration or database rollback is involved.
