## Release notes

This release improves the complete Model lifecycle: managing reusable Models, registering their primary files, sharing Textures, organizing uploads, and keeping Project Scenes pointed at current assets.

### Model administration

- Table order: selection checkbox, Name, Category, Options, Type, Status, Active, Size, actions. Sort all seven data columns, including Category. Options expose classifications such as Default, Public and Library.
- Narrow selection column and bulk deletion controls. Status uses colored text; Active uses a green check or gray X.
- Far-right icon opens the assigned primary file in a new tab; missing-file links are visibly disabled.
- Shared popup surfaces use opaque dark gray backgrounds, separating them from the main App without translucent content.

### Shared Textures and Model Files

- FBX bulk imports can satisfy a matching image dependency using an existing active Texture. The resulting Model File references the original Texture URL; no duplicate image Blob is uploaded.
- Reusable material assignment and named file dependency resolution remain distinct. A matching shared image can serve preview without automatically completing the saved dependency audit.
- Model Files distinguishes saved references, shared images available for preview, and genuinely missing files. **Link shared Texture** saves the existing URL reference and refreshes the audit; requirements have readable full-width rows.
- Attached files take precedence over filename fallback. Ambiguous filenames are not guessed, inactive Textures are excluded, and automatic library fallback remains owner-only and FBX-specific.
- Texture deletion and Model cleanup protect shared references. Existing duplicate images are not automatically removed.

### Storage and primary-file authority

- New uploads use readable names and UUID folders beneath `threed/users/<owner>/models`, `textures` and `previews`. Attachments follow the new primary asset folder; legacy primaries use a Model-ID attachment folder. Replacements receive unique URLs.
- Logical exporter filenames and relative paths remain separate from physical Blob keys. The Model Files form now explains that distinction.
- `threed_models.main_model_file_id` is the primary relationship. File URL and size live on `threed_model_files`; API responses derive those values from the assigned same-owner Model File.
- Creation registers and assigns the primary File. Deletion clears the primary relationship before deleting Files. Unassigned or obsolete URLs cannot satisfy Model readiness.
- No legacy backfill, old Blob relocation or bulk cleanup is included. The User explicitly accepted that old Models may require a new primary assignment.

### Scene and Character fixes

- Project loading refreshes current Model/File references rather than restoring obsolete URLs from marker JSON. Empty current references clear stale loaded visuals.
- GardenCharacter and EcctrlCharacter FBX loaders now resolve named images through current attachments or an eligible shared Texture URL instead of guessing the primary upload directory.
- Character **Save Position** refreshes its current Model and Files within the existing save transaction, preventing the response from resurrecting an old FBX URL.
- Generic Model fallbacks are grounded and visible independently of tiny import scales. Default: Sphere at 45% opacity. Per-Model choices include Box/Block, Rectangle, Cylinder, Pyramid and Torus, stored in existing metadata.
- Original Character cylinders and caller-owned procedural fallbacks retain priority. The reverted global placeholder selector and Project Assets warning panel are not included.
- Fallback meshes have no floating labels. Missing-file and observed generic loader errors appear in the selected marker's DetailsCard, with a Model Files repair link. Error reports are transient and clear with recovery/unmount.
- Placeholder geometry is visual only, not replacement collision geometry. Movement routing, external animations, task completion, world actions and the persistent Scene physics boundaries are preserved.

## Compatibility and rollback

Do not blindly redeploy v0.19.10c against the new schema: its code expects the removed Model URL/size columns. Prefer a scoped application fix compatible with primary-file authority. A rollback to an older application requires a compatible database restore or explicitly prepared schema restoration; restoring empty columns alone cannot reconstruct deleted references. Coordinate any such operation separately with the User.

Code rollback does not undo uploads, deletions, Texture links or Project position writes. Preserve existing database/Blob evidence; do not copy or delete files as part of an automatic rollback. Backup/export work and old-object reorganization remain separate future tasks.

Existing importer transport and format limits remain in force (including 4 MiB bulk files, 100 Models and 500 companions). Owner-library fallback is not public cross-owner Texture discovery. Missing-file fallback is a recovery display, not proof of a valid import, activation readiness or successful physics.
