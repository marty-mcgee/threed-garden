# v0.19.42 — ThreeD Ground Maps: Image Import + Scene Alignment

Status: Planning and discussion. Production is User-confirmed v0.19.41. No v0.19.42 schema or implementation is approved yet.

## Milestone goal

Allow a User to upload a PNG, JPG or WebP screenshot exported from a mapping program and use it as the flat visual ground of a ThreeD Project. The User can then align the image to the Project, place ThreeD Models, Characters, Beds, Plantings and FarmBots over recognizable roads, buildings and property features, save the Project, and receive the same ground alignment after reload.

The first release should import an image supplied by the User. It should not scrape a map site, capture third-party tiles, proxy provider APIs or generate an image from private provider URLs. The App should preserve entered source/attribution text and must not obscure attribution already present in an uploaded screenshot. Users remain responsible for ensuring their image may be uploaded and displayed.

## Prove — current implementation

- `InteractiveGround` in `src/components/map/ThreeDScene.tsx` owns the default visual grass plane, shadow receiver, pointer placement surface and fixed Rapier ground.
- The optional **Apply Ground Plane** control already saves `enabled`, `size` and `height` in versioned Project view state. Its material is currently a solid green surface.
- Environment Models are Project Model instances with `placementRole: environment`. They currently hide the default visual grass plane and own separate bounded surface/region collision preparation.
- Project Save/Restore persists ThreeD ground settings through `project.config.threeDViewState`; it does not currently identify a durable uploaded image asset or its alignment.
- `LeafletMap` already renders OpenStreetMap tiles, saves center/zoom, places/moves Project Models from geographic points and shares the Project marker projection system.
- Project administration already supports two local X/Z ↔ GPS calibration references. The shared projection code round-trips local Scene coordinates and WGS84 positions.
- The existing Model Texture API demonstrates authenticated owner-scoped image validation, bounded upload size, Vercel Blob storage, database ownership and guarded deletion. A Ground Map is a different domain asset and should not be represented as a Model material assignment.

## Product model

Keep three concerns separate:

1. **Ground visual** — procedural grass/color, uploaded image, or hidden.
2. **Ground physics** — one simple fixed plane/cuboid used for placement, Characters and movable objects.
3. **Environment Model** — optional ThreeD geometry with its own Box/Triangle collision policy.

An uploaded image changes the ground appearance only. It does not create terrain elevation, infer buildings, create collision meshes or replace an Environment Model. This separation keeps image resolution out of Rapier and avoids rebuilding physics when a texture changes.

The proposed Project Ground Map alignment is:

- image asset ID;
- enabled/visible state;
- center X and Z in Scene feet;
- width and length in Scene feet;
- Y height;
- Y rotation in degrees;
- opacity;
- optional source/provider and attribution text;
- optional geographic bounds or two image control points when Project calibration is available.

Image aspect ratio should be preserved by default. A deliberate **Unlock aspect ratio** option may permit correction for cropped or perspective-distorted screenshots, but should not be the default.

## Proposed workspace

Add a compact **Ground Map** section at the top of the existing Environment / Sunlight + Ground controls, following the ThreeD Blueprint:

- **Ground Visual**: Procedural, Uploaded Image, Hidden.
- **Choose / Upload Image** opens a focused dialog using existing upload patterns.
- Preview thumbnail, filename, dimensions and saved source attribution.
- Inline Width, Length, Height, Rotation and Opacity fields.
- **Fit to Project Bounds**, **Align North-Up**, **Reset Alignment**, **Save Project**.
- Optional **Align on 2D Map** mode for placing two geographic reference points.

The uploaded image should appear below ordinary Scene objects, remain selectable only while Ground Map editing is active, and never produce a normal Model DetailsCard or hover title.

## Development stages

### 1. Ground visual contract

Extract a bounded, framework-independent Ground Map contract and transform resolver. Define supported formats, pixel limits, byte limits, aspect-ratio behavior, transform ranges, opacity and source metadata. Add fixtures before UI or storage work.

Acceptance:

- invalid numbers, dimensions, MIME types and unknown fields fail closed;
- image-to-Scene UV orientation is explicit and North-Up does not silently mirror the map;
- the visual transform and physics plane transform share the same center, dimensions, height and rotation;
- legacy Projects continue to render their current procedural ground.

### 2. Durable upload and ownership

Preferred design: add a dedicated owner-scoped Ground Map asset record and a Project assignment/reference. Reuse the established Vercel Blob upload mechanics and path hygiene, not the `threed_model_textures` domain table. Store original filename, MIME type, bytes, pixel dimensions, blob URL, source/provider, attribution and timestamps. Delete the blob only when no owned Project still references it.

This stage requires explicit schema approval. If approved, use only the App protocol: update Drizzle schema, run `bun db:generate`, inspect the generated migration, then run `bun db:push` at the User-owned database gate. Do not create hand-written SQL files under `docs/`.

Acceptance:

- authentication and Project ownership are required;
- uploads are bounded and decoded/inspected server-side before registration;
- a failed database insert cleans up the uploaded blob;
- replacement and deletion cannot remove another User's file or a referenced asset;
- map-provider credentials, private URLs and browser object URLs are never persisted.

### 3. ThreeD rendering and controls

Render the Ground Map with a color-managed Three.js texture on the existing flat ground geometry. Preserve the fixed ground collider, pointer placement, deselection and shadows. Dispose replaced textures without remounting the Canvas or Rapier world. Use anisotropic filtering within renderer limits and cap decoded pixel area to control GPU memory.

Acceptance:

- image, procedural and hidden modes switch without duplicate planes or z-fighting;
- placement rays and physics align with the visible map plane;
- Environment Models may coexist with an explicitly enabled Ground Map;
- loading/failure shows a bounded fallback and does not delay unrelated Scene assets forever;
- image changes do not move existing Runtime Markers.

### 4. Manual Scene alignment

Deliver the reliable first workflow: upload, preserve aspect ratio, set real-world width, rotate, position and adjust height/opacity. Add a temporary edit outline and corner/axis guides only during alignment. Keep numeric fields authoritative and provide coarse/fine keyboard or button nudging without adding unrestricted R3F dragging to ordinary modules.

Acceptance:

- the User can align a known driveway or property boundary and then exit edit mode cleanly;
- **Fit to Project Bounds** uses current marker/Project extents with safe padding;
- **Align North-Up** uses the Project's established X/Z geographic orientation rather than assuming screen-up;
- Save/reload restores the exact Ground Map asset and transform.

### 5. Leaflet-assisted alignment

Reuse the existing Leaflet workspace and local/GPS projection rather than duplicating geographic math. Permit two image reference points to be matched to two Leaflet geographic points or existing Project calibration points. Solve translation, uniform scale and rotation; show residual error before applying. Require non-coincident points and retain manual adjustment afterward.

This phase aligns a User-uploaded image. It does not export or reproduce third-party tile layers. A later provider integration would require a separate review of that provider's API, attribution, caching and usage requirements.

Acceptance:

- two valid references deterministically solve image placement;
- reversed, coincident, nonfinite or implausible references fail without changing the saved map;
- existing marker local/GPS positions remain unchanged;
- 2D and 3D views show the same orientation and scale within documented tolerance.

### 6. Save/restore, loading and validation

Integrate the Ground Map reference and transform with explicit Project Save. Restore it before the Scene becomes presentable, while bounding failure so a missing image falls back visibly and completes loading. Do not save temporary edit handles, hover state, upload drafts or browser object URLs.

Run contract fixtures, upload/API ownership tests, Project session/view-state tests, Runtime Marker regressions, hidden-collision checks, image lifecycle tests, TypeScript and diff checks. Browser acceptance should cover desktop/mobile, image replacement, Project switching, reload, combined 2D/3D mode, Environment coexistence, Model placement, Character control and movable-ball contact.

## Recommended release boundary

The v0.19.42 checkpoint should include upload, durable Project ownership, manual alignment, ThreeD rendering, explicit Save/Restore and basic Leaflet-assisted two-point alignment. Terrain heightmaps, photogrammetry, automatic building extraction, live provider tile projection, bulk geospatial formats, offline tile caches and image-to-mesh generation should remain later versions.

## Development checkpoint 1 — upload, manual alignment and rendering

Implemented September 20, 2026:

- Added the dedicated owner-scoped `threed_ground_maps` table with one active image per Project, Project/owner foreign keys, immutable Blob URL metadata, decoded pixel dimensions, optional source and attribution, and guarded Project deletion behavior.
- Added authenticated `GET`, multipart `POST`/replace and `DELETE` endpoints. Uploads accept PNG, JPG and static WebP up to 16 MB and 16,777,216 decoded pixels. Database failures clean up the newly uploaded Blob; replacements remove the superseded Blob only after the new row is committed.
- Added a strict Ground Map transform contract to Project view state: visual mode, asset ID, center X/Z, width, length, height, Y rotation and opacity. Legacy Projects retain Procedural mode.
- Added a compact **Ground Map** Controls disclosure with source/attribution fields, upload/replace/removal, visual-mode selection, numeric alignment, opacity and **Align North-Up + Center**. Alignment remains part of explicit Save Project.
- Added a color-managed textured ground plane with bounded anisotropy. It reuses one fixed Rapier cuboid and the established pointer-placement path; uploaded pixels never generate collision geometry. Procedural and hidden modes retain the existing ground collision.
- Environment Models remain independent. An explicitly selected Ground Map can render beneath ordinary objects without becoming a Model marker, DetailsCard or hover title.

Schema protocol completed:

- `bun db:generate` produced one additive `threed_ground_maps` migration; the repository intentionally ignores generated Drizzle artifacts.
- `bun db:push` created the table. During live-schema synchronization Drizzle also normalized existing foreign-key constraint names plus the schema-declared Character animations and Layer config defaults. It reported no table or data drops.
