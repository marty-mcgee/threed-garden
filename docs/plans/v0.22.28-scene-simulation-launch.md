## Implementation and evidence

Implemented October 5, 2026. `ProjectSimulationLauncher.tsx` presents one green upper-centre Run/Stop button, a selector only for multiple choices, compact status and collapsed details. A click reads the selected saved records, starts the Scenario in memory and uses the page's existing Character control/Action Target state. Exact participant preparation rechecks Scene readiness, editing/placement, visibility, duplicate Character instances, movable-ball metadata and finite live position after asynchronous reads. A 20-second readiness timeout and Stop/manual-input/unmount guards prevent delayed execution. Project changes remount only the launcher for its Project identity; Canvas/Rapier and marker owners remain retained.

`GET /api/project/simulations` implements bounded summary paging and exact launch reads. It requires readable public/owned Project access, active owned Simulation/Scenario/module relationships, supported same-actor/ball Soccer Actions, active asset assignments and exact saved marker membership. Public output contains a parsed definition, minimal Scenario start descriptor and foot mappings only for the selected Character's own/inherited assignment keys. It exposes no owner IDs, arbitrary metadata/file URLs or results. Public/owner reads are no-store; existing private CRUD/results remain unchanged.

`ProjectSimulationControls` retains the single established runner in both modes. The public mode reads only the Project launch endpoint and never invokes journal capture/finalization. The owner mode still validates private records/revision and captures before navigation. Both modes monitor current participants, rig mappings, Scene scope and Sensor membership, then use correlated existing-owner arrival/contact outcomes and bounded observations. Collapsing details leaves the controls mounted. No general executor or new schema is included.
