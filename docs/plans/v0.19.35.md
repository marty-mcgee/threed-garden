Each step follows Prove → Act → Document. These are review areas, not assumed defects or authorization to rewrite Character runtimes. Define specific acceptance criteria from current implementation and User feedback before each scoped change.

## Acceptance criteria

- Selected Character and controlled Character are unambiguous; Take/Release Control remains predictable.
- Primary interaction controls are compact, discoverable and accessible; secondary sections do not dominate the Scene.
- Action availability, target identity/range, progress and failure feedback reflect actual runtime state.
- Filtering or toggling sections preserves action/selection state and editing drafts.
- Multiple Characters and Project switches do not leave stale interaction feedback.
- Existing animation loading, idle/walk/run, Garden wander, Ecctrl WASD, camera navigation and task-to-locomotion crossfades remain intact.
- Targeted Water/Pick Fruit, ball interactions and saved Project settings remain regression checks in Projects 8 and 15.

## Boundaries

Preserve separate GardenCharacter/EcctrlCharacter paths and isMovable routing, stable marker identity, one persistent Canvas/Rapier world, Character override → Model default precedence and first-pose gating. Animation and world mutation remain separate; world actions occur only after one-shot completion. Custom Slots remain animation-only.

No schema, harvest persistence expansion, new gameplay effects, cross-project borrowing, MQTT/device operation or Admin restructuring is included. Any later schema change requires explicit approval and uses only `bun db:generate` followed by `bun db:push`; no manual SQL artifacts. Package remains at the stable release until code development begins.
