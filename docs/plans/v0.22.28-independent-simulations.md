## Authoritative Developer direction

October 5, 2026: the Developer stopped the combined Scenario/Simulation progression and confirmed **independent definitions; choose Project/modules when running**. This supersedes the [earlier launch candidate](v0.22.28-scene-simulation-launch.md). That candidate is not a completed implementation of this corrected architecture.

| Object | Responsibility | User action |
| --- | --- | --- |
| ThreeD Scenario | A plan and its setup/guidance | Open Scenario |
| ThreeD Simulation | Ordered Actions, participant roles and observation requirements that connect ThreeD modules | Run Simulation |
| Simulation run | Chosen Project, participating modules and exact participant/Sensor bindings for one attempt | Prepare, Run, Stop |
| Simulation Results | Captured definition/revision, execution context, Action responses and observed measurements | Inspect/analyze |

A Simulation is not a Scenario child. Opening a Scenario is not a prerequisite for running a Simulation. Definitions are not owned by a Project or a ThreeD module. Authentication ownership still controls private definition editing and result access. Project/module authorization is checked against the context selected for each run.

## Prove: current implementation differs

The Developer explicitly directed removing **all Scenario ties from the ThreeD schema**, including both definitions and Results, on October 5. This step removes their `scenarioId` columns, Scenario foreign keys/indexes and Drizzle relations; updates dependent reads/writes/forms/runtime contracts; and generates the native Drizzle migration for review without applying it. No Scenario table, definition Action JSON or finalized result report is deleted. Existing historical snapshot JSON is retained as historical data, not a new relational link. Project/module independence remains the next distinct refactor; this correction must not silently expand that paused work or change public authorization.

Before this correction, both tables had Scenario links, and CRUD, capture, readiness and launch used them. Affected implementation: `src/libraries/schema/threed/index.ts`, Simulation input/runner/Scene/launch/result contracts, private Simulation/results APIs, Project launch API, Admin forms/list and Scene launcher/controls. Acceptance: no Scenario column/FK/index/relation, no Scenario query or selector, no Scenario-start prerequisite or state mutation during Run, and no changes to existing Actions/reports, authorization, revision checks or result finalization.

Result capture currently obtains its context from the saved definition. The v0.22.27 result snapshot/report contract and finalized history must remain intact while new runs adopt an explicitly selected context. Existing definition JSON contains concrete Project marker/Sensor identifiers; dropping its columns alone would not make those definitions reusable.

## Required implementation contract

1. **Independent definitions.** Revise the Drizzle definition object and CRUD around authenticated owner, ID, name/slug, description, bounded definition, revision, availability and timestamps. Remove required Project/module/Scenario parent bindings. Choose a collision-safe owner slug policy before replacing the old Project/module uniqueness constraint.
2. **Roles and module connections.** Definitions describe the required module capabilities, Action sequence and participant/observation roles. Use an explicitly versioned definition contract so existing marker-based definitions can be retained and migrated without pretending their identifiers work in another Project. Preserve existing Actions and observation information; do not silently pick replacement assets.
3. **Run preparation.** Choose the Project and participating modules, then bind each required role to an authorized asset/Sensor in that context. The current Scene may supply the Project as an initial choice, not as the definition's owner. Show a readiness checklist and enable Run when all required bindings are valid. Opening a Scenario remains a separate UI action and does not change these choices.
4. **Execution and Results.** Resolve a bounded execution snapshot from the saved revision and validated bindings before dispatch. Owner capture receives and rechecks the chosen execution context, then stores that context, exact resolved Actions, outcomes and observations. Keep idempotent run UUIDs, capture-before-dispatch, immutable finalization and save-only retries. Retain honest failed/cancelled/timed-out/unfinished attempts and historical reports.
5. **Public/private access.** Preserve the Developer's public local-run/private owner-result decision. Decoupling definitions must not expose an owner's entire private Simulation catalog through any public Project. Introduce an explicit publication or assignment contract for which independent definitions a visitor may run. Do not broaden public access by removing the old join predicates alone.
6. **Retained runtime boundaries.** Use the established Character navigation/contact-kick and physics/Sensor owners. Keep one Canvas/Rapier world, exact correlation, first-pose/visibility/editing guards and Stop/stale-reply cancellation. The first supported executor remains bounded Soccer Actions; independent schema does not authorize arbitrary module Actions, physical commands, MQTT, automatic Project saves or implicit cross-Project asset copying.
