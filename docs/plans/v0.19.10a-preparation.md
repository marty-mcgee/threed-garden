# v0.19.10a Stage 2 — FBX batch preparation

Status: design completed September 9, 2026, following the [Stage 1 audit](v0.19.10a-audit.md). This document records the preparation design. Stage 3 has since implemented the dedicated Models entry point; the [implementation record](v0.19.10a-implementation.md) describes validated behavior and the tighter 4 MiB transport limit. Stage 1 documentation changes were present at the start and are preserved.

## Problem and scope

The existing bulk queue cannot reliably prepare files for the current single-Model contracts: it omits primary registration, disagrees with attachment-directory validation, and provides no practical way to resolve ambiguous textures or incomplete configuration.

The first implementation will prepare FBX batches using the existing authenticated Model workflow. Preparation stays in browser memory. Choosing files, editing defaults, matching textures, removing rows, and scanning references perform no upload or database mutation. **Import ready Models** is the explicit start of uploads and creation. Existing single-Model formats remain available through Add Model.

The changed files for this design step are this specification and the parent development plan. Implementation owners and acceptance criteria are recorded below; runtime and API changes belong to Stage 3.

## User flow

1. Open **Bulk Import FBX** beside **Add Model** in the Models workspace once the implementation checks pass.
2. Choose multiple FBX files, then add texture files to a shared selection pool. Review each row's original filename, editable Model name, file size, and preparation state.
3. Apply batch defaults and inspect the selected row's configuration and texture matches. Resolve ambiguous matches, supply missing files, or explicitly choose **Configure textures later** for that Model.
4. Select **Import N ready Models**. Only eligible rows in the current reviewed batch are processed; blocked rows stay available for correction.
5. See a result for every attempted Model. Each created Model has **Review Model files** linking to `/admin/threed/model-files?modelId=<id>` for preview, dependencies, material assignments, and repair. Standard Model editing remains the place to change configuration and activation afterward.

Use one selected-row detail area rather than a Canvas for every queued item. This initial preparation surface does not promise local FBX rendering: the existing preview uses an uploaded or saved Model. Visual inspection continues through the shared preview after creation. A later pre-upload preview would need separate proof of local-file lifecycle and dependency resolution.

## Selection and identity

- Accept `.fbx` primary files, case-insensitively, up to the existing 100-Model queue bound. Report unsupported and excess selections without deleting existing rows. Add only the available number of rows and identify skipped files.
- Reject zero-byte primaries and files above the upload route's `256 * 1024 * 1024` byte limit before reading their contents. This is the application limit, not proof that the deployed request transport supports that size; Stage 3 must verify practical upload limits before presenting them as supported capacity.
- Give every queue row and selected texture a stable local ID. Preserve the original filename and any supplied relative source path separately from editable Model names and attachment destinations.
- Name, size, and modification time can identify a possible repeat, but cannot establish identical content. Do not silently merge same-named files from separate selections. Show a possible-duplicate notice and allow the User to remove a row. A known selected File object can be reused without adding another copy.
- The first surface uses multiple-file selection. Folder traversal, ZIP extraction, and automatic folder-bundle inference are deferred; keep any source-relative paths supplied by the selection mechanism without inventing absent directories.
- Scan one primary at a time and release its byte buffer afterward. Retain File references and bounded scan results, not every decoded FBX in memory. A late result from a removed or replaced file must not update another row or start importing it.

## Shared files and texture association

The shared pool contains local files, not saved Texture records. The initial FBX companion choices are PNG, JPG/JPEG, WebP, TGA, and BMP, matching the existing bulk component. Preview images remain optional, separate per-Model inputs with the upload endpoint's JPG/PNG/WebP and 5 MB validation. Do not reinterpret a thumbnail as a material texture.

Adding a file to the pool does not attach it to every Model. Each row owns its dependency-to-file choices and attachment destinations. One pool File may be selected by multiple Models, producing Model-owned attachments for those Models through the current files route. Removing a pool entry invalidates every unsaved association that refers to it and recalculates readiness; it never deletes saved assets.

Use these matching rules in order:

1. Prefer an unambiguous normalized relative source-path match when that path is available. Resolve a source reference relative to the primary's known directory within the same selection root; do not invent a common root for loose files. Show the candidate and destination in the row review.
2. Otherwise suggest a file only when its basename is unique among the relevant pool candidates. Mark the suggestion visibly and allow replacement.
3. If multiple candidates share that basename, show **Choose texture** with each candidate's available source path, size, and selection identity. Never choose the first file silently.
4. If no candidate exists, show **Missing** and allow adding/selecting a file or deferring texture configuration for this Model.

Candidate selection and runtime resolvability are separate checks. Evaluate the resulting attachment set per Model using the released exact-path/unique-filename rules. The presence of a same-named texture elsewhere in the batch must not satisfy this Model's dependency. Flag competing suffix matches, such as `textures/wall.png` and `vendor/textures/wall.png` for one request, before execution; the existing resolver can otherwise choose by attachment order. Adding or moving an attachment must re-evaluate previous matches. Do not change shared runtime resolution as part of this preparation step.

| Reference and selection | Destination and preparation result |
|---|---|
| `textures/walls/Barn_Wall.png`, one matching file | Preserve that valid relative destination; matched |
| `Barn_Wall.png`, one matching file | Use `textures/Barn_Wall.png`; matched by unique basename |
| Workstation reference reduced by the scanner to a basename | Use a Model-owned directory; retain the discovered reference for review, not as a storage path |
| Two candidate `wall.png` files | Require explicit selection; preserve distinct source identities |
| One Model requires `walls/wall.png` and `roof/wall.png` | Allow separate destinations; one selected File may intentionally serve both references |
| Two attachments leave a basename-only request ambiguous | Block that match until the attachment set resolves unambiguously, or defer configuration |

Attachment destinations must pass the same normalization as the files API, include a directory no longer than 100 characters, and be unique case-insensitively within one Model. Prefer a discovered safe directory; use `textures` for bare filenames. Do not silently truncate paths or append arbitrary suffixes to resolve collisions. Reject unsafe paths and ask for a valid destination in the row. Absolute exporter paths are never recreated in storage.

Missing references and an empty reference scan require different messages. Zero detected references means **No named textures detected — review after import**, not “texture complete” or “valid FBX.” Server structural analysis still runs before Blob storage. Embedded-texture and binary-FBX cases need representative validation before treating scanner output as authoritative.

## Reusable Textures and material configuration

The initial design deferred reusable Texture assignments to Model Files because upload analysis did not expose material targets. Following visual testing, the User requested **Assign Existing Texture File** during bulk preparation. Stage 3 now includes an optional batch selection with per-Model inheritance, override and None. The existing Textures workspace still owns reusable Texture master records; this extension creates no new masters or material channels.

The implemented bulk picker offers active owned Textures. The existing server FBX parse now derives the same bounded material inventory as the preview, rather than guessing target keys. Import requires all 1–500 supported material slots when a Texture is selected, uses the existing `baseColor` assignment action, and verifies saved assignments before activation. See the [implementation record](v0.19.10a-implementation.md) for request bounds and failure handling.

Show unresolved named dependencies until the existing audit reports otherwise; a Base Color assignment does not fulfill those filenames. **Resolve missing texture files later (keep inactive)** still applies a selected reusable Texture during import while leaving the Model inactive for remaining-file review. Normal, roughness, metallic, and other material-channel expansion is outside this stage.

## Defaults and per-Model review

| Field | Initial value | Editing rule |
|---|---|---|
| Model name | Suggested from FBX filename | Per Model; non-empty after trimming |
| Scale | `1.0` | Batch default with per-Model override; finite and at least `0.01` |
| Y rotation; X/Y/Z offsets | `0.0` | Per Model; finite numbers, matching the single editor |
| Categories | None | Batch default with per-Model override; existing owned categories |
| Existing Texture | None | Active owned Texture for all Base Color slots; batch default with per-Model inheritance, override or None |
| Library Item | On | Batch default with per-Model override |
| Public | Off | Batch default with per-Model override |
| Used by Plants / Characters | Off | Batch default with per-Model override; no automatic runtime classification |
| Active after import | Off | Explicit opt-in per batch or row; forced off for deferred texture configuration |
| Preview image | None | Optional per Model; no effect on texture matching |

The inactive default is an intentional change from the dormant bulk component's active default, allowing review before Library use. Batch-default changes affect only fields still inheriting that default. A row override survives subsequent default changes; **Use batch default** clears that override. Show the effective values before import.

The selected-row review covers these fields and planned attachments. Advanced animation, LOD, and arbitrary metadata editing stays in the established Model editor. Bulk classification does not create Characters, Plants, Project markers, or assignments to a Project.

## Readiness and execution handoff

| Preparation state | Meaning | Included by Import |
|---|---|---|
| Scanning | Reference scan pending | No |
| Needs attention | Invalid file/configuration/destination, unresolved duplicate, or missing/ambiguous dependency without a decision | No |
| Ready | Valid local preparation; detected dependencies matched, or no named references detected | Yes; server analysis still required |
| Ready — configure later | Valid primary/configuration; User explicitly deferred unresolved texture work | Yes, as inactive/pending |
| Imported / failed / outcome unknown | Result of an attempted import | Never silently included as a new Model |

Use one readiness calculation for counts, row labels, button state, and the submitted selection. The button reads **Import N ready Models**, is disabled at zero, and shows separately how many rows need attention or will remain inactive for configuration. For example, 3 ready, 1 configure-later, and 2 blocked rows submits exactly 4, leaves 2, and identifies the deferred Model.

At click time, freeze the eligible rows' effective fields and selected attachments for that run. Disable repeated submission and mutation of the active batch until it finishes. Deferred Models omit unresolved attachments; invalid selected destinations or files must still be corrected or removed. Deferral never bypasses Model-file or field validation.

Stage 3 must retain the upload response's `fileName`, URL, size, type, and analysis, build the existing Model payload with `primaryFile`, and create each Model inactive/pending before attachments. Confirm primary registration and saved attachments before reporting import completion. A non-deferred Model may be activated only when explicitly requested and the saved dependency audit succeeds without unresolved references. Failed or unavailable audits leave it inactive and identifiable for review. No-reference scan results are not a visual-quality guarantee.

Run Models sequentially. Continue with unrelated eligible rows after a failure. Preserve known successful Model IDs and attachment results; offer correction through the existing workspace once creation is known. Treat a lost response as **Check import result** rather than blindly creating again. Reconciliation, staged-upload cleanup, and retry controls must be proved before exposing writes; a durable queue, background service, or new database schema is not assumed.

## Acceptance examples for implementation

1. Selecting files and changing defaults makes zero mutation requests. Removing a scanning row cannot restore it through a late callback.
2. The queue cap and file-size checks run before file reads. Scans are sequential; unsupported files are individually identified.
3. Same-named FBX files with equal sizes/timestamps remain distinct rows unless the User removes one. Two same-named texture candidates require a visible choice.
4. `Barn_Wall.png` matched to `textures/Barn_Wall.png` is ready and accepted by attachment-directory validation. Two distinct directories containing `wall.png` preserve exact-path resolution.
5. One source image may serve multiple Models or two explicit destinations on one Model. Removing it recalculates all affected unsaved rows; an unrelated row is unchanged.
6. A changed batch scale updates inherited rows and preserves an overridden scale. Empty names, non-finite transforms, and scale below `0.01` block only their rows.
7. Mixed ready/blocked/deferred rows produce the exact documented count and request set. Configure-later creates an inactive/pending Model and lists its remaining work.
8. Zero detected FBX references displays an inspection limitation. Server-rejected FBX input produces no Model creation; subsequent eligible Models can proceed.
9. Imported Models have a primary file row and `mainModelFileId`; Model Files can inspect them and offers the existing texture and material workflow. Reusable Texture selection never fabricates a filename match.
10. A repeated click, lost response, or retry does not silently create duplicate Models. Known created Models always have a review destination, including attachment failures.
11. Single-FBX importing, Model Files, Library placement, and Scene behavior remain unchanged. No Project state, physics, Character runtime, or schema changes are introduced by batch preparation.

Checked the proposed handoff against current single-import payload construction, primary registration, attachment normalization, runtime matching, and material-assignment code. An independent code review found no blocking design contradiction after clarifying source roots and suffix conflicts. Documentation-link, newline, whitespace, and `git diff --check` checks passed for this step.

The Stage 1 import validator (8 groups) and TypeScript checks passed against the unchanged application code; they were not repeated for this documentation-only step and do not validate the proposed UI. Stage 3 requires new focused checks for implemented preparation behavior plus relevant TypeScript and browser/API verification from the repository validation ladder.
