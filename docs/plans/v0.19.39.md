# v0.19.39 — ThreeD Characters: Models, Meshes + DetailsCard

Status: Released to production; deployment User-confirmed. Package `0.19.39`. No schema changes were required.

## Goal

Refine Character Models, visible meshes, basic defaults and the Scene Character DetailsCard as one coherent experience across Projects. Keep the compact ThreeD Blueprints and make reusable Character/Model settings versus Project-instance settings clear. Exact requested defaults and visual changes will be confirmed during the first development stage rather than inferred from the version theme.

Admin Character management lives in src/components/admin/threed/characters/ThreeDCharactersCRUD.tsx; shared assignments/previews live in src/components/admin/threed/animations/CharacterAnimationAssignments.tsx. Existing DetailsCards expose Character interactions, grouped animation actions, control/camera settings, physics, Save/Move/Remove and on-demand Help. v0.19.38 adds explicit click-to-reposition with released-control checks. Inspect the full affected path before modifying defaults, meshes or editor behavior; this inventory does not establish a specific defect.

1. **Prove Character defaults and ownership.** Inventory existing Character and linked Model defaults, active primary Files, transform/scale precedence, fallback shapes, materials, skeleton/mesh loading and readiness. 2. **Refine Model/mesh presentation incrementally.** Address verified rendering or default inconsistencies in the narrowest owner. Preserve primary File authority, shared textures, model origins/grounding, first-pose gating and imported FBX rig compatibility. Review visual bounds separately from Character capsule/feet collision geometry; do not automatically substitute animated mesh colliders. Avoid merging the two Character runtimes or adding model-specific hardcoded behavior.
3. **Tighten Character DetailsCard.** Apply compact collapsible sections for identity/model information, interactions/animation categories, Project placement and physics. Preserve Save/Move/Remove placement, Take/Release Control and existing target behavior. Keep explanatory text in Help or collapsed details. Provide keyboard focus, accessible names, touch targets and disabled-action explanations on demand. Do not claim a Model/animation is usable before runtime verification.
4. **Verify persistence and Project isolation.** Preserve released position/physics/facing behavior through edits and movement, Project Save and reload. Any additional proposed field must have explicit ownership, validation, restoration and legacy fallback defined before implementation. Keep reusable Character/Model sources unchanged when editing Project instances. No new state/schema is authorized by this planning step.
5. **Validate each increment and obtain browser review.** Follow Prove → Act → Document. Test relevant TypeScript, static assets, Character position-save, assigned animations, animation restart, Library placement, Runtime Marker, Project session and orchestration checks. Add meaningful checks for demonstrated issues. User reviews development before production release preparation; User owns the build/deployment gates.

## Acceptance criteria

- Character identity, assigned Model and Project placement remain consistent from selection through editing/movement and Save/reload.
- Defaults have documented precedence and preserve existing records unless the User approves a migration/change.
- Missing/unusable Models settle into the established fallback and recovery UI without hanging Project loading.
- Garden and Ecctrl Characters retain their separate movement owners, animation loading and readiness rules.
- DetailsCard remains compact and legible, with supportive explanations available through Help, accessible controls and no overlapping workspace panels.
- Idle/walk/run, Garden wander, Ecctrl WASD, Take/Release Control, one-shot task crossfades, targeted Water/Pick Fruit and existing harvest persistence remain intact.
- Changes to one Character do not move, remount or mutate unrelated Project assets.

## Boundaries and release outline

No schema edits, database commands, environment-file edits, SQL documentation folders, new physical operations, arbitrary dragging or harvest/world-persistence expansion. Schema changes require separate explicit approval and the User's bun db:generate / bun db:push protocol. Preserve the persistent Canvas/Rapier world and stable marker identity. Root CONTEXT.md is currently absent; archived context is historical and current implementation remains authoritative.
