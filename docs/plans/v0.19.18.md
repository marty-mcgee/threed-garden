## Approved local storage

The preset stage adds two owner-scoped tables; leave existing source, clip, Model and Character assignment schemas intact:

- `threed_animation_presets`: serial id, user_id, name (varchar 120), description (text, optional), revision (positive integer, default 1), created_at and updated_at. Nonempty trimmed name, owner/name uniqueness and composite id/owner uniqueness.
- `threed_animation_preset_entries`: serial id, user_id, preset_id, action_key (varchar 64), mode (assigned/disabled), nullable animation_id, created_at and updated_at. Unique preset/action; composite preset/owner FK with cascade on preset deletion; composite animation/owner FK matching the existing library pattern. Assigned requires an animation ID; disabled requires null. Index animation_id for usage checks. Action keys use the existing allowlist in server validation.

No Blob copies, source uploads, preset FK on Characters, old-data migration, or automatic live DB update. Applying a preset writes independent existing assignment records; later editing/deleting the preset does not alter previously applied Characters.

## Navigation audit and policy foundation

Inspected `DetailsCard.tsx`, `ThreeDScene.tsx`, `EcctrlCharacter.tsx`, GardenCharacter movement references, `interaction-core.ts`, `action-target-core.ts`, and the Character/Marker architecture guides before editing. Concrete findings:

- DetailsCard already resolves current target position and gates controlled Character interaction range. Its current out-of-range instruction is manual WASD.
- Ecctrl already supplies target-relative forward direction and calls `setMovement` for controlled WASD. Automatic walking must feed this established controller, so existing locomotion chooses Walk/Idle and Rapier retains collision authority.
- GardenCharacter remains inside a fixed Scene parent. Moving its visuals toward a target would not establish a correct moving collider; do not reuse the Ecctrl adapter or add automatic Garden movement in this step.
- Ecctrl position edits already queue translation and velocity reset into `useBeforePhysicsStep`. Teleport must use that ownership boundary, after collision/grounding verification, rather than changing a rendered group or issuing body writes from UI handlers.
- The existing target-relative approach is planar and cannot prove a clear route or a valid landing surface. Target center/origin is not itself a safe landing coordinate.

Implemented the isolated `navigation-core.ts` policy and `validate:threed-character-navigation` fixture. It produces steering/state only: walking, arrived, cancelled or blocked. Runtime inputs explicitly include current target/Character positions, control/availability/task state, manual input, horizontal stopping distance and a separate vertical arrival tolerance. It cancels on unavailable target/actor, control release, manual input or task start, and stops after four seconds without meaningful progress or a two-minute limit. Terminal requests cannot restart. These timing values are initial bounded policy defaults, pending browser experience.

Validation passed: TypeScript, diff checks, the new pure navigation fixture and all 18 existing orchestration groups. No Scene runtime, movement, DetailsCard control, physics object or database behavior was changed by this foundation step.

## Walk to Target — Ecctrl adapter implemented

The navigation foundation is now connected to the movable Character runtime. `CharacterNavigationControls.tsx` adds **Walk to Target** and **Stop Walking** beneath the selected target in a Character DetailsCard. Take Control and a live Character position are required. Non-movable Garden Characters show an availability explanation; their movement/collider path is unchanged.

`useCharacterNavigation.ts` handles client-only, request-correlated navigation intent for one stable actor marker. Scene marker groups expose stable names for lookup. The adapter resolves the target's current world-space bounds on each active frame, checks actor/target ancestor visibility, and produces steering through the tested policy. Clearing/changing target, releasing control or runtime teardown cancels through effect cleanup; manual WASD/jump/run input, task lock, hidden/removed targets and hidden actors cancel on the next frame. Stop Walking ends steering explicitly. Requests for another actor are ignored. Arrival/cancellation/blockage publish navigation status only, never semantic task completion or a world-action API call.

Ecctrl feeds automatic steering through the same `setForwardDir` and `setMovement` path used by manual controls, with run/jump disabled. The existing locomotion controller chooses the Walk/Idle animations and retains the loaded Model. Physics, camera and live-position reporting remain owned by Ecctrl. No save happens automatically; existing Save Position / Save Project remain the persistence gates.

Clearance implementation refinement: this first adapter uses conservative world-space visual bounds plus capsule clearance, avoiding new per-frame Rapier queries. It does not claim to compute the exact collision surface. Large/concave or loosely bounded targets can stop farther away, and a colliding route can report blocked after four seconds without progress. This is direct steering, not obstacle pathfinding. It is deliberately not reused as teleport landing verification.

Validation passed: TypeScript, diff checks, navigation policy/adapter fixtures, the actual Ecctrl movement-frame fixture, all 18 orchestration groups and Character animation restart/first-pose fixtures. Tests use real Three.js bounds and mocked controller/event interfaces; browser physics/appearance acceptance is pending. No build or live DB writes were run. Existing unrelated preset/category changes and the user-owned FBX deletion were retained.

## Teleport near Target — implemented, browser acceptance pending

User confirmed Walk to Target works for both Farmer Kate and Farmer Joey at two different target locations. That confirmation covers walking; teleport remains a separate local test.

Proved the remaining gap: the DetailsCard navigation controls and intent contract exposed only walk/stop. Ecctrl already owns explicit position edits through a before-physics-step translation and velocity reset. This step adds `useCharacterTeleport.ts`, `teleport-landing.ts`, and the DetailsCard button, extending the existing navigation intent contract and cancelling active automatic walking on teleport. Acceptance: one explicit request moves only its controlled actor to verified clear ground near the current target, retains facing and the loaded Model, and leaves the Character unchanged when no landing is available. No automatic save or action-completion event.

The adapter queues intent until the physics-step boundary, rechecks control, visual readiness, task lock, target identity and actor/target visibility, then queries the current Rapier world. Effect cleanup discards pending intent on target/control changes and unmount. Stop or a new walk replaces a queued teleport. Translation plus zero linear/angular velocity use the existing Ecctrl body; normal runtime reports update marker/camera position afterward. GardenCharacter remains unchanged.

Landing search is bounded to 48 candidate points around the target's world-space bounding box, preferring the actor-facing side. Each candidate requires five supported ground samples, a slope no greater than 30 degrees, at most 0.2 scene units of footprint height variation, and a clear upright capsule. Ground must be fixed, nonsensor geometry within 3.5 units below to 0.75 units above the target bounds' minimum Y. Other Characters and obstacles block occupancy; the actor's own body and sensors are excluded. This is conservative local surface sampling, not a navigation mesh or a guarantee for every concave/oversized target. No acceptable candidate produces a short message and no position write.

### Teleport ground-normal correction

User reported that step 2 returned **No clear ground near this target**. Reproduced offline using the actual Scene ground construction: `InteractiveGround` renders a Drei Plane rotated -90 degrees around X, which the parent `RigidBody colliders="cuboid"` converts to a zero-depth cuboid. Rapier 0.19.2 returns a downward normal for a downward ray hitting this coincident-face surface. The signed slope check rejected it; previous ground tests used cuboids with nonzero thickness and missed this case.

Acceptance: recognize the Scene's flat ground without accepting steep planes, solid undersides, unsupported landings or occupied capsules. Changed only the landing slope classification in `teleport-landing.ts`: cuboids with exactly one zero half-extent use the absolute vertical normal; solid shapes retain the signed upward-normal requirement. Scene geometry, walking, physics bodies and landing occupancy checks remain unchanged.

Added real Rapier fixtures for the exact rotated Scene plane at Y=-0.03, a steep plane and a ray starting inside a solid. The Scene-plane fixture failed before the correction and passes afterward. TypeScript, teleport and walking fixtures, and diff checks passed. No build or DB commands ran. ### Teleport proximity correction — target collider authority

User's Project #8 screenshot showed both Characters too far from the targeted Bed after teleport. Inspection proved two causes: `Box3.setFromObject(target)` included the Bed's large animated PulseRing, and globally sorting all candidate rings by distance from the actor favored the farthest clearance on the actor-facing side. Acceptance: prefer a small clear gap beside the actual target collider, independent of highlight size, while retaining ground/occupancy checks and avoiding nearby Characters.

`useCharacterTeleport.ts` now resolves target-owned colliders from R3F's collider state objects and their Scene ancestry. `teleport-landing.ts` projects outside probes onto those collider surfaces, respecting their current position/rotation. Visual bounds only establish outside probe reach and ground-search height; they no longer supply the landing perimeter. At most 16 nearby enabled nonsensor target colliders are sampled from 17 directions each. Missing colliders leave the actor in place. Clearance tiers are tried in order: capsule radius plus 0.1, 0.35, then 0.75 scene units. Distance from the actor orders candidates only within each tier, so another close side wins before a farther ring.

The expanded real-Rapier fixtures also exposed a capsule-overlap false negative for a fully enclosed landing near a symmetric box corner. Added a point-containment rejection alongside capsule overlap. Both exclude the actor and sensors; target and obstacle collisions remain enforced. This changes only teleport landing selection, not walking, collider creation, animation, or persistence.
