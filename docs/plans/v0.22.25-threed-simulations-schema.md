## Implemented schema

Developer confirmed October 4, 2026 that the targeted SQL executed successfully in Neon SQL Editor and `threed_simulations` is in the production database. Earlier statements below describe the agent's prior preparation/comparison; the agent did not apply the migration or verify the live database. Application deployment remains separate. The requested [Admin implementation](v0.22.25-simulation-admin.md) now builds on this table without another schema change.

`threedSimulations` uses serial `id`, required `userId`, `projectId` and `threedId`, nullable `scenarioId`, bounded `name` (120) and `slug` (100), optional `description`, JSONB `definition`, positive `revision`, `isActive`, and created/updated timestamps. It is available from the central schema export with `ThreeDSimulation`, `NewThreeDSimulation` and `ThreeDSimulationDefinition` types. Drizzle relationships resolve owner, Project, ThreeD module and optional Scenario; the ThreeD relationship includes its Simulations collection.

The definition envelope is `{ version: 1, steps: [], observations: [] }` by default. Its check rejects non-object JSON, missing/null keys, unsupported version and non-array steps/observations. Nested Action/observation vocabulary remains open objects pending a dedicated input parser; SQL shape checks and TypeScript types do not validate Actions, sensor metadata, bounds or readiness. New definitions are inactive with revision 1. Active only denotes availability and never starts execution. `updatedAt`/revision must be advanced by future explicit writes; no automatic trigger is added.

Slugs are unique within Project + ThreeD module. Additional indexes cover owner + Project, ThreeD module and Scenario. Foreign keys cascade on owner/Project/module deletion. Scenario deletion sets the optional link to NULL and retains the definition. Existing Scenario tables, constraints and behavior are unchanged.

Foreign keys validate row existence, not owner/Project/module correspondence. Before future creation/update, verify authenticated ownership of every referenced row, actual module assignment to the Project and matching Scenario owner/Project/module. JSON steps/observations must receive a strict bounded parser and reference authorization before any API or runner is introduced. No data entry or execution path is shipped by this step.
