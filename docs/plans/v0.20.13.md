# v0.20.13 — Bun Removal

## Status

Planned at the User's request, separately from the v0.20.12 production checkpoint. No Bun-removal implementation is authorized by this planning step alone. The User intends to release v0.20.12 now; deployment confirmation remains pending.

## Objective

Standardize application tooling on Node.js and npm: development, dependency installation, Drizzle commands, utilities, workers, CI and deployment configuration. Preserve application behavior, dependency versions where possible, and the existing Neon/Drizzle/PostgreSQL architecture. This is a tooling migration, not an Assembly feature or database migration.

## Proven starting points

- CI configures Node 24 and Bun latest, installs using `bun install --frozen-lockfile`, runs TypeScript via Bun, and executes validation through npm.
- `bun.lock` is the current dependency lockfile; README installation instructions use Bun.
- Multimedia import and the FarmBot MQTT worker explicitly use `bun run`.
- Source search found no direct `Bun.*` or `bun:` API usage in src; this is preliminary evidence, not proof of runtime equivalence.
- Drizzle package scripts already invoke Node explicitly to address the Bun terminal-input failure; strict confirmation remains enabled. Preserve this narrow existing fix during migration.

## Incremental implementation plan

1. Inventory tracked scripts, runtime APIs, CI, installation instructions and actual deployment settings. Confirm the Node version supported by the installed app/dependencies and deployment; use one explicit version policy across environments.
2. Produce a package-lock.json and compare resolved versions against bun.lock. Avoid silently turning the migration into dependency upgrades. Keep the old lockfile until the replacement install and comparison succeed.
3. Replace Bun-only utility/worker launch commands with Node plus the existing TypeScript runner where appropriate. Preserve script names and behavior.
4. Change CI to npm ci and npm-run commands; remove Bun setup. Align local instructions, runtime declarations and deployment install/build overrides after verifying the actual hosting configuration. Do not infer remote settings from example files.
5. Validate from a clean npm ci installation. Run TypeScript and the repository CI validation group, plus offline worker and Multimedia checks appropriate to changed launch paths. Verify Drizzle startup and interactive input without applying a production schema. The User owns npm run build and production smoke acceptance.
6. Remove bun.lock and obsolete active Bun instructions once the replacement is validated. Preserve historical release records. Document rollback and release handoff before deployment.

## Acceptance

A fresh checkout installs, checks, develops and builds with the documented Node/npm workflow without Bun. CI no longer installs Bun. Utility and worker entry points start under Node; tests must not connect to MQTT or operate physical devices. Drizzle remains the schema source of truth and retains confirmation; no --force workaround. Dependency/version differences are reviewed and reported. Package manager migration introduces no unrelated schema or feature changes.

## Boundaries and unresolved work

Do not edit environment files or expose connection strings. Remote deployment changes require the existing authorized workflow and a concrete reviewable configuration. Do not apply schema changes merely to test the CLI. The unrelated schema drift seen during v0.20.12 db:push remains a separate database review; removing Bun does not resolve it.

The existing v0.20.12 Assembly work remains separate: local Front-End composition, Admin assignment shell, approved Drizzle tables and ORM demo services. Database application, live demo creation/readback and future Scene integration retain their own checkpoints.
