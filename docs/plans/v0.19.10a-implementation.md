# v0.19.10a Stage 3 — FBX bulk-import implementation

Implemented September 9, 2026. This is development work; no deployment or real upload was performed. Existing Stage 1/2 documentation changes were preserved. Package version remains `0.19.10-alpha`.

## Result

The dedicated `/admin/threed/models` workspace now offers **Bulk Import FBX**. Select FBX files, add a shared pool of local textures, review per-Model matches and settings, then import ready rows. Preparation does not upload or persist anything. Blocked rows remain available for correction, and Models explicitly deferred for texture configuration remain inactive/pending.

Names, transforms, category selections and flags are validated before import. Defaults can be overridden per Model and restored to inheritance. Same-named files retain separate identities; ambiguous textures require a choice. Valid destination directories preserve the existing exact-path/unique-filename runtime behavior. Additional texture attachments are supported when an FBX contains no discoverable named references.

Imports execute sequentially through existing owner-scoped endpoints. Primary creation includes the single-Model `primaryFile` payload, creating the Model and primary attachment together. The runner saves one attachment per request, reads back the primary and attachments, and audits saved dependencies. Activation is off by default and requires explicit opt-in plus a successful dependency audit. Structural analysis still happens in the upload endpoint; reference scanning is not proof of valid geometry or complete materials.

Every known created Model has a **Review Model files** link that opens a new tab, retaining the current batch. Refreshing the Models list after a run keeps the bulk component mounted. The Project-embedded CRUD keeps its existing single-Model workflow to avoid its parent refresh discarding batch results.

## Concrete implementation decisions

- **4 MiB per file:** this bulk-only ceiling includes primaries, textures and previews, leaving multipart overhead below Vercel's 4.5 MB Function request limit. The single upload route's 256 MiB validation value is not deployed transport capacity. Larger-file support requires a separate upload-transport implementation; this stage does not add it. See [Vercel server uploads](https://vercel.com/docs/vercel-blob/server-upload).
- **Bounded local work:** at most 100 Models, 500 selected texture files, and 500 discovered references per primary. File reads run sequentially across chooser events. Too many references blocks that row rather than silently truncating it to a complete result. Matching uses destination indexes to avoid repeatedly comparing every pair for every reference.
- **Owned previews:** a validated preview is saved after Model creation as an `other` attachment under `previews/<filename>`, then assigned as `thumbnailUrl`. This avoids a detached standalone preview upload if a later operation fails. Preview basenames must differ from detected texture references and selected texture attachments because the existing resolver can also see supportive files.
- **Separate Texture workflows:** a local image reused across Models creates Model-owned attachments. The batch does not create reusable Texture master records, infer material target keys, or expand material channels. Use Model Files after import for existing reusable Texture assignments.
- **Definitive rejection versus uncertain outcome:** a rejected pre-create operation allows explicit correction/retry only when any known staged primary was successfully discarded. Lost, timed-out, server-error, or malformed create responses never automatically retry or delete a potentially committed primary. Known Model IDs remain available for review after attachment or verification failure.
- **Bounded responses:** runner responses are limited to 1 MiB and requests use a 120-second abort deadline. Aborting a mutation is not proof that the server rolled it back.

## Remaining manual and later-stage work

Before releasing this implementation, import representative real FBX files through the authenticated deployment: bare/relative/duplicate texture names, missing textures, embedded textures, and a corrupt FBX. Verify primary registration, saved attachments, dependency audit, Model preview, explicit activation and Library/Scene placement; repeat single-FBX import/configuration and the relevant Character/Scene regressions. Confirm an actual near-limit multipart upload in the deployment.

Queue state is tab-local. Refresh/navigation loses local selections and results; there is no durable batch resume or automatic server reconciliation of an unknown create. Known partial imports are repaired through Model Files. **Correct and retry** is limited to confirmed pre-create failures; uncertain outcomes require checking Models first. **Clear imported rows** clears successful results only. Stage 4 can improve repair/result management without treating successful Models as new imports, and Stage 5 covers downstream real-asset validation.
