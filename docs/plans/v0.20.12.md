## Intended scope

- Use imported FarmBot component assets as ordinary reusable ThreeD Models, preserving the established Model, primary File, Texture and Animation workflows.
- Introduce general-purpose ThreeD Assembly Groups that reference component Models, with per-component position, rotation and scale relative to an assembly origin. A Model may appear more than once in an assembly.
- Let Users arrange components, save a reusable Assembly Group in the database, and place that assembly in multiple Projects and Scenes. Project-instance transforms must not mutate reusable source Models.
- Use FarmBot as the first assembly example and ThreeD FarmBot Demo as the intended demonstration Project.

These are version objectives, not approval of a particular schema or runtime implementation. Proceed in small, reviewed steps. Imported components remain ordinary assets; this scope does not introduce a separate FarmBot-only Model format.

## Step 1 — Read-only review and minimal proposal

Review completed. No application code, schema, API or runtime edits were made in this step.

### Proven current behavior

- `src/libraries/schema/threed/index.ts`: `threedModels` owns the reusable primary File reference, base scale, degree-based Y rotation, offsets and publication flags. Files and materials remain attached to that reusable asset.
- `src/libraries/schema/project/index.ts`: `projectThreedMarkers` owns Project/user scope, stable marker identity, source asset identity and world position.
- `src/app/api/project/threed-markers/route.ts`: ordinary Model placement registers a Project asset assignment and a unique `models-<uuid>` marker. The marker stores instance rotation X/Y/Z and scale multiplier separately from the reusable Model. There is no assembly relationship in this placement path.
- `src/components/map/details/ModelInstancePlacementEditor.tsx`: current controls edit a Model placement's position, Y rotation and scale, rather than an assembly's relative component transform. The UI converts radians to degrees for display.
- `src/components/threed/markers/ModelMarker3D.tsx`: asset configuration transforms are applied before loaded bounds are used to ground the Model. Using this unchanged for every assembly component would independently reposition component origins vertically.

### Proposed contract (not a database schema)

| Concept | Proposed minimum data | Responsibility |
| --- | --- | --- |
| Assembly definition | Stable ID, owner, name, revision, components | Reusable arrangement independent of a Project |
| Component | Stable component ID, referenced Model ID, label, local position XYZ, local rotation XYZ, positive uniform scale | One occurrence of a Model relative to assembly origin; repeated Model references allowed |
| Project assembly placement | Stable placement ID, Project/owner, assembly ID and chosen revision, world position XYZ, rotation XYZ, positive uniform scale | Where one assembly is placed, without modifying the reusable arrangement |

Use existing Scene units, Y-up coordinates and radians in the contract; display degrees in editors. Euler order must be explicit (proposed XYZ). Uniform scale keeps the first contract small. Keep source Model configuration separate from component and placement transforms; never multiply source scale twice.

Proposed transform order: placement transform × component-local transform × source Model configuration × authored mesh transform. Assembly rendering must preserve authored component origins and suppress per-component automatic grounding. Any placement grounding belongs to the aggregate assembly bounds; it must not rewrite stored component transforms. Existing standalone Model behavior must remain unchanged.

Proposed initial save behavior: editing an assembly definition is explicit; moving a placed group saves only that Project placement. Existing placements should retain their selected assembly revision until an explicit update, preventing edits to one reusable arrangement from silently moving other Scenes. This does not by itself freeze referenced Model files/materials; asset revision behavior needs a later explicit decision before claiming fully immutable assemblies.

Authorization must cover both the assembly and all referenced Models; public visibility of the group cannot expose private components. Missing/unavailable Models should produce a visible incomplete-group state, not automatic record deletion. Referenced-definition and Model deletion policies require resolution with the persistence design.

### Small first example and acceptance

Use a local preview arrangement of three occurrences: one FarmBot: Box and two FarmBot: Belt Clip references. This is a transform/reuse demonstration, not a claim of mechanically correct FarmBot assembly. Resolve actual Model IDs and inspect their origins/dimensions when loading the preview; do not invent IDs or fit coordinates from filenames.

The first contract exercise should prove:

1. Two occurrences of the same Model retain different component IDs and transforms.
2. Moving/rotating/scaling a group preserves relative component placement, including an elevated component.
3. Two Project placements remain independent and do not modify source Models or each other.
4. An unchanged definition survives serialization with IDs, radians and transforms intact; malformed references, duplicate component IDs and non-finite/non-positive transforms are rejected.

## Step 2 — In-memory contract implemented

User authorized the contract/transform step after reviewing the proposal. Added `src/libraries/services/threed/models/assembly-group-core.ts` and the offline `threed-assembly-group` validation task. The module imports Three.js math classes only; it does not load Models, initialize a renderer, contact providers, authorize users or write state.

Definition format version 1 includes owner/name/revision and 1–100 components with distinct stable occurrence IDs. Repeated positive integer Model references are allowed. Placements carry Project/owner identity and must match the selected definition ID/revision. IDs are non-empty strings up to 128 characters; names/labels up to 255. Parsers reject unknown properties, numeric strings, missing data, non-finite transforms and duplicate occurrence IDs. Position bounds are ±1000000 Scene units, rotation bounds ±10000 radians, uniform scale 0.0001–10000, matching the existing Model instance transform bounds. These are initial in-memory limits, not an approved database schema.

Parsers return independent copies; serialization validates definitions. Transform resolution returns column-major placement × component matrices using XYZ Euler radians and positive uniform scale. It performs no grounding and does not apply source Model configuration; the future asset loader must apply that configuration exactly once. Referenced Model existence, visibility, revision storage and access checks remain responsibilities of a future persistence/runtime integration. Placement and definition owners may differ for legitimately shared assemblies; accepting the data does not grant access.

Validation passed: `npm run validate -- threed-assembly-group` (five groups), `npm run typecheck`, and diff whitespace review. Fixtures cover JSON roundtrip, repeated Model references, copy isolation, elevated component placement, rotated/scaled groups, independent Project placements, component and placement transform composition, invalid IDs/revisions, unknown fields, bounded component counts and invalid numeric transforms. Fixture Model IDs are synthetic; no live asset records were queried.

This completes the agreed minor step. No database schema, API, Scene renderer, assembly UI or package version changes. Next review should choose a small preview integration and resolve authored origins/source configuration before saving any assembly to the database.
