# v0.20.1 — ThreeD Physics

Status: **release candidate accepted; automated validation passed; build success and browser acceptance confirmed by the User; production deployment pending**.

## Milestone goal

Connect ThreeD Module data, Rapier physics, and live FarmBot MQTT observations through one clear application contract. Soccer and Farming will be the first reference scenes:

1. **Soccer** proves that Models, collision surfaces, sensors, balls, goals, and match rules can exchange normalized physics events.
2. **Farming** proves that confirmed FarmBot position and status data can update the corresponding ThreeD Model safely and accurately.
3. **ThreeD Layers** organize the resulting objects, zones, events, and diagnostics without owning their state.

The Scene should explain what is physically happening, where it is happening, and which source reported it. Scene simulation, observed equipment data, and commands sent to equipment remain separate.

## Proven current state

The repository already contains:

- a persistent React Three Fiber Canvas and Rapier world in `src/components/map/ThreeDScene.tsx`;
- fixed, dynamic, cuboid, ball, and triangle-surface collision paths;
- stable Project marker identity through Runtime Markers and `project_threed_markers`;
- owner-scoped FarmBot credentials and read-only MQTT sessions;
- normalized FarmBot status and position events, persistence, and Dashboard presentation;
- a provider-neutral MQTT service under `src/libraries/services/threed/mqtt`;
- dormant FarmBot command, acknowledgement, timeout, recovery, and emergency-stop machinery;
- disabled production command executors and no shared MQTT publish operation; and
- ThreeD Layers with ordered configuration and Scene visibility controls.

The implementation should connect these established systems. It should not create another MQTT client, FarmBot command route, marker registry, physics world, or Layer state authority.

## Product language

### Physics event

A **physics event** is a bounded ThreeD Scene fact derived from Rapier. Examples include sensor entry, sensor exit, contact start, contact end, impact, rest, and wake. It uses stable Project object identities without exposing mutable Rapier handles.

### Live equipment state

**Live equipment state** is the most recent confirmed, normalized status received from an external integration such as FarmBot MQTT. It carries its observation time, freshness, and connection condition. A ThreeD Model presents that state but does not become authority over the physical equipment.

### Scene simulation state

**Scene simulation state** is produced locally by Rapier and scenario rules. A Soccer score or a FarmBot Model entering a visual work zone remains Scene state until a separately authorized server operation persists or acts on it.

### Equipment command

An **equipment command** is an authenticated, audited, semantic request sent through the existing FarmBot command pipeline. Physics events and Scene animation completion do not automatically become equipment commands.

## Architecture and authority

```text
FarmBot MQTT observation
        ↓
existing server-only FarmBot adapter
        ↓
normalized live equipment state
        ↓
coordinate + freshness adapter
        ↓
existing Runtime Marker / ThreeD Model
        ↓
ThreeD Layer visibility and diagnostics

Rapier callback
        ↓
provider-neutral ThreeD physics event
        ↓
Soccer or Farming scenario rule
        ↓
bounded Scene simulation state

deliberate User equipment action
        ↓
existing authentication + policy + audit boundary
        ↓
future separately approved MQTT command gate
        ↓
device acknowledgement
```

Authority rules:

- Runtime Markers own stable Scene object identity.
- Rapier owns active Scene physics.
- The FarmBot integration owns normalized observed equipment state.
- Scenario reducers own temporary Soccer or Farming simulation state.
- ThreeD Layers own visibility, grouping, order, and diagnostics only.
- Existing command policy, audit, worker, and acknowledgement services own equipment commands.
- MQTT data does not directly mutate arbitrary Rapier bodies.
- Rapier events do not directly invoke MQTT or FarmBot commands.
- Character animation completion remains separate from equipment acknowledgement.
- The browser never supplies raw topics, CeleryScript, command names, pins, durations, or unrestricted physical coordinates.
- Credentials remain server-only.
- Telemetry and Layer changes must not remount the persistent Canvas, Rapier world, or unrelated Runtime Markers.

## Physics API decision

The first Physics API will be a versioned internal TypeScript contract rather than a public HTTP mutation endpoint.

```ts
type ThreeDPhysicsEventV1 = {
  version: 1;
  projectId: number;
  sceneEventId: string;
  kind:
    | 'sensor-enter'
    | 'sensor-exit'
    | 'contact-start'
    | 'contact-end'
    | 'impact'
    | 'rest'
    | 'wake';
  source: ThreeDRuntimeMarkerIdentity;
  target?: ThreeDRuntimeMarkerIdentity;
  occurredAt: string;
  magnitude?: number;
  point?: { x: number; y: number; z: number };
  tags?: readonly string[];
};
```

Implementation must reuse the actual Runtime Marker identity contract. Event identity, timestamps, magnitudes, positions, and tags must be validated and bounded. High-frequency contacts must be deduplicated or rate-limited before entering React state.

No database persistence is needed to prove this contract. Durable match history, event replay, or analytics would require a later approved schema stage.

## FarmBot interface decision

Use FarmBot interfaces according to their established responsibilities:

- REST API for resource metadata and existing server-side validations;
- MQTT Message Broker for live status and position observations through the existing worker;
- CeleryScript/RPC for future commands through the existing semantic command pipeline; and
- FarmBotJS as a research checkpoint only, without installation or runtime replacement unless it proves a missing required capability.

The current server-side MQTT.js worker already implements identity validation, subscriptions, normalization, persistence, reconnection, and safety boundaries. FarmBotJS should not replace it merely to wrap existing functionality.

## ThreeD Layers decision

ThreeD Layers may organize and toggle:

- live FarmBot position and connection presentation;
- physics sensor and diagnostic zones;
- Soccer goals, field bounds, and event diagnostics; and
- Farming work envelopes, tool zones, planting zones, and no-go regions.

Layers must not store live positions, hold Rapier objects, process MQTT messages, or dispatch commands. Begin with the existing `custom` Layer type and validated configuration. The current enum does not require a schema change until implemented UI or query behavior proves that dedicated types are necessary.

### v0.20.1.12 — Scene TransformControls: sensor pilot

**Prove:** Sensor editing exposed numeric fields and one surface-placement click, but no axis handles for vertical adjustment. The placement/zoom formulas also used the opposite Y-rotation sign from Three.js. The installed Drei package already exports TransformControls; no dependency or schema change is needed. Affected boundaries: the Scene page, DetailsCard sensor editor, Scene camera/physics coordination, and a new shared transform workspace.

**Act:** Added a shared draft transform workspace and Drei TransformControls gizmo. Each sensor has **Transform Sensor · Mouse Handles**, **Move XYZ** (world axes), **Rotate Y** (sensor-local axis), live local-coordinate feedback, **Save Transform**, and **Cancel**. Escape discards the preview. Save uses the existing authenticated marker metadata update; a failed request retains the draft. Pointer movement writes no persistent data and moves no saved collider. Physics pauses for the editing session; camera-follow and auto-rotation suspend without changing the selected camera mode, and OrbitControls suspend while a handle is dragged. Selection/layer/editor cleanup removes the session. Other Scene hosts without the transform provider remain supported.

The preview follows the owner's actual rendered rigid-body pose. Sensor dimensions retain Scene units, independent of visual Model scale. Placement and zoom now use tested Three.js world/local conversion, including tilted owners. Y rotation is derived from the quaternion so turning past 90 degrees does not reverse the rotation.

**Validate:** TypeScript, diff checks, Soccer physics and Runtime Marker validators passed. New deterministic coverage compares owner-local conversion with actual Three.js scene-graph transforms, checks an explicit positive 90-degree rotation, full-range yaw, and invalid coordinates. Browser drag/save/cancel/reload acceptance remains pending; this is not a production acceptance claim. The User retains the build gate.

**Resolution:** Sensor adapter implemented, shared editing foundation available. Whole-Model editing is the next adapter stage, not yet enabled by this pilot.
