# v0.33.0 plan: ThreeD Terrains

## Goal and status

Introduce **ThreeD Terrains** as a capability of the existing ThreeD Top Module. A Project should be able to present a terrain in its 3D Scene and a useful, aligned counterpart in its 2D Design plan. The Developer supplied the standalone example in ignored `reference/terrains`; its source was inspected without running it. The approved SQL was manually applied by the Developer. Terrain services, Project Save/load and the initial Scene surface are implemented locally; the 2D counterpart and browser acceptance remain pending.

The intended result is a **smooth terrain surface** saved as a reusable ThreeD asset and placed in multiple Projects, comparable to Assembly Group reuse. It serves as the Project's Environment Map surface: grounded Models, Characters, and other applicable objects stand, are placed, and move at its elevations. Intentional vertical offsets and existing runtime physics remain valid. The Developer chose this direction after reviewing the supplied block-based example. Exact authoring controls, file format, storage, and collider implementation remain to be designed.

## Current App boundary

- The active 3D Scene is owned by `ThreeDScene.tsx` and its persistent Canvas/Rapier world. `SceneEnvironment.tsx` supplies the procedural ground presentation and placement surface.
- A Project may own one `threed_ground_maps` image record. Its flat image transform is stored in versioned Project view state and saved through Project Save. The current visual modes are procedural, image, and hidden. This **Ground Map** is not yet a 3D terrain.
- A reusable Model placed as an Environment/Base Map is another existing path. That role provides the behavioral precedent, but does not make a Terrain definition a Model or turn the Project-owned Ground Map image into a reusable record. Keep the reusable Terrain definition and each Project placement distinct.
- The 2D Design plan and 3D Scene share Project scope and coordinate conversions. Existing Project content, architecture, marker IDs, layers, physics owners, selection, and Save/load must survive Terrain work.

## Source-to-owner mapping

- **Reusable definition:** `threed_assembly` and its revisions demonstrate owner-scoped reuse, but an Assembly is a composition of Models. The current `threed_ground_maps` row is unique per Project, so it cannot be the reusable Terrain definition. A dedicated Terrain identity is the likely fit; its exact schema and authorization contract require an approved persistence proposal.
- **Project assignment and placement:** `project_assets` relates typed assets to a Project and ThreeD Module instance, while `project_threed_markers` stores placed Runtime Marker snapshots. The `asset_type` enum has no Terrain value, and the marker-type enum is limited to plantings, beds, characters, farmbots, and models. A Terrain needs an approved typed assignment and stable Project placement identity; do not store it as a fake Model, Assembly component, or Ground Map image. Preserve explicit Project Save.
- **Scene presentation and physics:** `ThreeDScene.tsx` owns one persistent Canvas/Rapier world. It currently mounts an image Ground Map with a flat cuboid collider, an optional extra flat ground, or `InteractiveGround`; Environment Models have separate bounded surface/region collider handling. `InteractiveGround` returns `y=0` placement points, and the Model Library drag target intersects a `y=0` plane. Both need Terrain-aware hits when a Terrain is active.
- **2D Design:** `DesignPlan.tsx` renders Model plan images in X/Z and edits Project placements. The Terrain counterpart needs the same coordinate transform and a surface-height lookup for 2D placement edits; the 2D drawing must not become a separate Terrain save owner.

## Proposed ground-source behavior for the first slice

One Project Terrain placement is the **active ground surface** at a time. Its visible mesh, placement hit testing, and fixed Rapier collider must use the same deterministic elevation data and Project transform. A second placement of the same reusable definition in another Project has independent transform and Save state. Grounded objects contact that surface; existing Y offsets, airborne objects, native architecture elevations, and runtime physics are not forcibly flattened.

**Developer-confirmed coexistence rule:** the Project explicitly chooses one active ground source. When Terrain is active, keep the Project Ground Map image and Environment Models saved and addressable, but use the Terrain for placement and ground contact within its footprint; do not also mount an invisible flat collider there. Environment Models remain visible, and their structural colliders may remain active, but an Environment Model intended as ground must not silently compete with the Terrain as placement authority. Outside the Terrain footprint, use the Project's existing flat ground; define and test the boundary so a Model or Character cannot fall through or jump at the seam. A Ground Map image remains a flat reference; draping it over Terrain is separate work. If the Terrain is removed or disabled, restore the prior flat/image/Environment ground behavior. This is accepted direction, not current App behavior.

**Flat Model platform above Terrain:** the Developer confirmed that both the Terrain and a flat soccer-field Model stay visible in the same Project. The field is a separate Project Model placement at its own elevation; it does not deform to follow Terrain. Where their footprints overlap, the field surface should sit above the Terrain without raised Terrain breaking through it. Terrain supplies ground contact where exposed, while the field's existing Model collider supplies contact on the platform. Preserve both saved identities and transforms; never silently lift or flatten a saved Model. The 2D Design plan must show both footprints and retain their independent selection. Architecture Levels are a separate drawing feature and do not own this surface layering.

## Persistence contract for implementation review

The confirmed plan establishes the relationship and behavior, but does not itself apply a database change. The candidate contract is:

1. A **reusable, owner-scoped Terrain definition** in the ThreeD Top Module, with a stable identity, bounded deterministic elevation inputs, and a revision. Saving a definition must not mutate an already saved Project placement silently.
2. A **Project assignment** to a saved ThreeD Module instance, with the existing owner and Project checks. `project_assets.asset_id` is integer and its `asset_type` enum has no Terrain value. A Terrain identity must fit that junction or use a separately approved typed relationship; a UUID cannot simply occupy the integer field.
3. A **Project placement and active-ground choice**, separate from the definition. It needs a stable placement identity, source Terrain and revision, Project transform, and active-ground state. `project_threed_markers` currently covers Models, Characters, Beds, Plantings, and FarmBots with integer source IDs; adding Terrain there would change its established marker contract. Prefer a dedicated placement record unless further source review finds a typed Project placement owner that fits. Explicit Project Save/load remains the workspace commit path.
4. **Deletion and conflict safety:** do not leave Projects pointing at missing Terrain data. Resolve definition deletion while assigned, and preserve drafts on revision conflicts. Removing the active placement restores prior ground behavior without deleting Ground Map or Environment Model records.

Before a schema edit, review exact fields, constraints, authorization, API shape, Project Save transaction, and rollback/migration steps as one focused proposal. Do not run production SQL or `db:push` as validation.

### Approved additive schema contract

Use **integer Terrain IDs** so the existing `project_assets.asset_id` can represent a Terrain without changing its identity type. Add these tables and one enum value; no existing row is rewritten.

| Table / change | Columns and constraints |
| --- | --- |
| `threed_terrains` | `id integer generated by default as identity primary key`; `user_id text not null references "user"(id)`; `name varchar(255) not null` with nonblank check; `created_at` and `updated_at` timestamps not null, default `now()`. Index `(user_id, name)`. This is the reusable catalog identity, not a Project placement. |
| `threed_terrain_revisions` | `terrain_id integer not null references threed_terrains(id) on delete restrict`; `revision integer not null check (revision > 0)`; `format_version integer not null check (format_version = 1)`; `width_m` and `length_m double precision not null check (> 0 and <= 1000)`; `columns` and `rows integer not null check (between 2 and 129)`; `heights_m jsonb not null`; `appearance jsonb not null`; `created_at timestamp not null default now()`; primary key `(terrain_id, revision)`. A validated, immutable row contains the canonical height samples. Application validation requires exactly `columns * rows` finite heights in row-major order, each between -1000 and 1000 metres, and a bounded appearance object. The mesh, 2D lookup and collider consume the same saved sample array. |
| `project_terrain_placements` | `id text primary key` (generated UUID), `user_id text not null references "user"(id)`, `project_id integer not null references project(id) on delete cascade`, `threed_id integer not null references threed(id)`, `terrain_id integer not null`, `terrain_revision integer not null`, `center_x_m` and `center_z_m double precision not null`, `rotation_y_deg double precision not null`, `scale double precision not null check (scale > 0)`, `saved_at timestamp not null default now()`. Unique `(project_id)` enforces one active Terrain placement per Project. Composite foreign key `(terrain_id, terrain_revision)` references `threed_terrain_revisions(terrain_id, revision)` with deletion restricted. Index `(user_id, terrain_id)`. Application validation bounds all transforms and verifies the Project owner, active `project_threed` assignment, matching Terrain owner, and matching active `project_assets` row. Placement elevation remains `y=0` in the first slice so its zero-height border meets the flat ground. |
| `asset_type` enum | Add `threed_terrains`; an assigned Terrain uses `project_assets.module_type = 'threed'`, its saved ThreeD Module instance ID, `asset_type = 'threed_terrains'`, and integer `asset_id = threed_terrains.id`. No `project_threed_marker_type` value is added. |

**Revision and Save contract:** Definition edits create a new immutable revision; they do not change existing Project placements. The Project owner explicitly selects a revision. Project Save writes placement changes in the existing row-locked snapshot transaction, with the same conflict stamp and failure behavior as other Project state. Loading a Project joins the placement to its saved revision and validates its active assignment before exposing public Scene data. A Project with no placement keeps its existing Ground Map/Environment behavior. A Terrain with Project references cannot be deleted until those references are removed; deletion never cascades into Project content. Keep the prior tables and data if code is rolled back after adoption.

**Boundary rule for the first slice:** Store zero-height samples around the complete outer border and constrain the placement base to `y=0`. The existing flat ground covers space outside the footprint and stops at its boundary; there is no hidden flat collider under the hills. Visual mesh, placement ray hits and fixed collider share the same border vertices. Test rotated and scaled borders and reject a placement whose transform cannot maintain a continuous edge. This is a conservative starting contract, not a promise that arbitrary raised/clipped Terrains already work.

The Developer approved this schema proposal and manually applied the [SQL migration](../developers/sql/threed-terrains-v0.33.0.sql). The matching Drizzle definitions, owner-scoped Terrain service, Project Save/load placement and initial Scene surface are implemented locally. The 2D Design counterpart and browser acceptance remain pending. Code rollback retains populated Terrain tables and references; do not revert to code that ignores active placements after they contain data.

## Supplied example: source findings

`reference/terrains` is a Vite/React Three Fiber demo named `3d-terrain-r3f`, with a screenshot and a README linking to the upstream project by jsulpis. Its README credits inspiration from Faraz Shaikh. The included `three-noise.module.ts` says it borrows code from Faraz Shaikh's `three-noise` package and includes other noise-code attribution. No top-level LICENSE file was found in the supplied folder; verify upstream permissions and attribution before copying any implementation into production.

- `useSquareSurface.ts` creates a square grid. The default Resolution of 0.3 produces a 150 × 150 grid, or 22,500 blocks, in an 8-unit-wide visual preview. These are demo units, **not** established ThreeD Scene metres.
- `useFbmNoise.ts` and `useProceduralTerrain.ts` sample seeded fractal noise, apply Scale/Height/Detail/Fuzzyness controls, and elevate blocks. In color mode, heights below the water threshold are visually clamped to that threshold.
- `Terrain.tsx` renders one instanced mesh of colored boxes, rotated into the ground plane. `useNaturalColor.ts` selects Water/Shore/Beach/Shrub/Forest/Stone/Snow colors by height; `useHeightMap.ts` provides a diagnostic height-color display. The screenshot illustrates that output; it is not a ThreeD App capture.
- The demo uses its own Canvas, lighting, OrbitControls, Zustand/Immer settings, and Leva controls. Its package targets older React/Three/R3F versions than the App. Its default Seed is random on load and Regenerate changes it; saving a seed would be necessary for repeatable Project restoration.
- The source contains **no** Project identity or Save/load, 2D Design counterpart, Terrain collision/placement rays, Rapier bodies, or mobile acceptance. The Leva color setup assigns the same key twice, so the threshold control is overwritten by the color control in that object; copy neither its UI nor dependencies wholesale.

**Accepted visual direction:** adapt the example's seeded height-and-color concept into a continuous height-field mesh with smooth shading inside the existing Canvas. Its block/voxel renderer is reference behavior, not the target. Use explicit Scene dimensions and a deterministic preview. One saved Terrain definition can be assigned to multiple Projects; each placement retains its Project-specific transform and Save/load identity. A continuous surface also avoids treating the example's 22,500 visual blocks as independent physics colliders.

## Work stages

1. **Complete source intake.** Confirm upstream license/attribution. The Developer chose a smooth surface; the local source and screenshot establish the demo's seeded elevation/color behavior, but do not establish a production license, Scene-unit scale, performance target, or browser acceptance. Treat `reference/` as inspection material, not production source or browser-executed code.
2. **Implement the approved persistence contract.** The additive Drizzle schema and matching manual SQL were reviewed and the Developer applied the SQL. Owner-scoped revisions and Project Save checks are implemented locally. Do not rerun the SQL or use full `db:push`.
3. **Build a bounded generator and preview path.** Adapt only the needed seeded height/color behavior into typed, validated App code. Sample heights on a bounded grid, form a continuous mesh, and compute normals for smooth lighting; use elevation colors without introducing visible block seams. Keep source units explicit and convert through existing Scene/metre conventions. Bound grid density, geometry size, memory and update cost; keep the seed stable across redraws. Avoid arbitrary JavaScript execution or wholesale adoption of the demo's Canvas, UI and older dependencies. Show a preview before Save or Project assignment.
4. **Integrate with Project and Canvas owners.** Use existing owner authorization, draft/revision checks, Project Save/load, and resource lifecycle. Derive visual elevation, placement ray hits, 2D placement height, and the stationary ground collider from the same Terrain geometry so Models, Characters, and other grounded objects contact the visible surface. Replace flat `y=0` placement assumptions only for an active Terrain. Preserve intentional height offsets, runtime movement, selection, 2D/3D coordinate alignment, and the inactive Ground Map/Environment Model state. Do not replace the persistent Canvas/Rapier world or remount unrelated markers.
5. **Verify and prepare release.** Reuse one Terrain in two Projects and verify independent placement and Save/reopen. Test a small and a realistic surface for smooth lighting, seams, and bounded load cost. Verify 2D/3D placement, selection, ground contact without hovering or falling through, Character movement over slopes, other applicable object movement, layers, Project switching, Scene restoration, and mobile viewport access. Run focused checks, fresh TypeScript, offline CI, and an isolated build as applicable. Record Developer browser/device acceptance separately from automated results and production evidence.

## Decisions to make after example review

- What authoring controls and revision behavior should a saved Terrain definition expose, versus controls on its Project placement?
- The one-active-ground-source rule is confirmed. Exact seam geometry and hit behavior at Terrain edges still need implementation design and acceptance.
- What should the 2D counterpart show: a top view, contours, boundaries, imagery, or some combination?
