## Implemented user flow

1. Open the owned **ThreeD Soccer** Project with its existing persistent ThreeD Scene.
2. Choose **Practice Soccer** through the Project Scenario controls and satisfy its existing setup/readiness checks. Start the Scenario explicitly; loading alone remains configuration.
3. Select the assigned **Farmer Kate** Project instance and use **Take Control**. Check the rig/first pose, current Ecctrl body, visible Character Layer and mapped run/foot-kick animation readiness.
4. Choose an assigned, visible movable-ball instance. The Simulation's saved target binding must identify that exact Project marker; use the established Action Target controls/identity.
5. Choose the active, owner-scoped Simulation **Run to target ball then kick the ball**, linked to the loaded/started Scenario. Show actor, ball, ordered steps and readiness before enabling Run.
6. Run once: **Run to target** waits for correlated navigation arrival, then **Kick ball** requests the existing contact kick. Report completion only after the ball owner's correlated `applied: true` result.
7. Show running step and a bounded result summary, with Stop available. A miss, unavailable clip/rig, hidden target, changed control, timeout or blocked approach produces an honest terminal result.

The title describes an authored definition, not a hardcoded special case in the engine. Initial execution capability is deliberately the two Soccer steps; pre-existing unsupported execution types must be rejected with a clear reason rather than silently played or reported complete.

If the Scenario has no active Simulation, **Prepare Soccer Simulation** opens `/admin/threed/simulations/new` with the Project/module/Scenario, current controlled actor, current ball target and Sensor Group as an editable draft. It supplies the milestone name and two ordered Actions (60-second Run, 30-second Kick, Stop on failure), remains inactive initially and performs no write until Save. Review choices, enable Active and save. Return to the Scene, load/start the Scenario if needed, Take Control/select the target, and refresh the Simulation choices. A draft URL grants no ownership; normal owner-scoped choices and POST validation still apply.

One Soccer definition uses one Character and one exact ball. Other saved Action types remain definition-only. A navigation interruption, failed approach or timeout always stops the sequence, even when that step says Continue; it never advances to a kick. Continue applies to failed kick steps, and the overall outcome remains failed if any step failed. A navigation-only definition reports navigation completion without claiming a kick.

Run captures the saved revision and checks it again after asynchronous exact reads; changed revisions require review and a second Run. Project/Scenario switches abort pending preflight. During execution, manual keys, replacement navigation/Actions, control/target/Layer changes, missing participants, placement/editing, mapping/Sensor membership changes and timeouts stop progression. Cancellation invalidates the pending request before synchronous cancellation replies, removes listeners/timers and clears matching queued contact samples; a newer unrelated navigation request is left alone. The existing contact path rejects unsupported rig points and misses without a completion impulse.

Optional observations retain at most 32 group summaries, count at most 256 accepted group events and capture baseline/final counter totals without resetting shared counters. The accepted counter ref is updated before notifying run readers, so a same-physics-step kick result sees the current count. These are **run-window observations**, with reset/truncation indications; neither kick completion nor sensor activity proves an Action caused a goal. Collection ends with the run, before any later ball entry. No result rows, automatic Project saves, new migration, cross-Project reuse, FarmBot/worker/MQTT or physical-device operation are introduced.

## Implementation checkpoints

### 1. Definition vocabulary and Project binding

- Extend the strict version-1 Simulation input vocabulary with explicit navigation and ball-kick operations, retaining existing definitions and bounds. Implemented Action identifiers are `runToTarget` and `kickBall`.
- Keep the existing `threed_simulations` envelope/columns. No migration or run/results table is required for this milestone.
- Add readable Admin Action labels and compatible actor/target choices. Validate owner, Project/module, Character instance and movable-ball metadata on save/readiness; a name or reusable Model ID cannot substitute for the marker ID.
- Carry the chosen Scenario ID/module binding into the Scene's active runtime context. Keep legacy saved guidance compatible; restored labels alone must not authorize execution.
- Save/Active continues to mean definition availability only. Run is a separate explicit Scene operation.

### 2. Run to target through the current Ecctrl owner

- Extend navigation intent/state to express running while preserving existing Walk, Stop, manual WASD and camera-relative movement behavior.
- The adapter continues to produce steering. Ecctrl retains movement velocity, animations, live position, body ownership and grounded/first-pose gating.
- Resolve the target's current live position/visible bounds each frame. Stop outside its collision bounds; never move a visual transform independently of its body or teleport to the ball.
- Correlate navigation status to the run/step/request and exact actor/target. Arrival must be an authoritative status, not a fixed delay or completion of a run animation.
- Manual input, control release, missing/hidden participant, task conflict, placement, Project switch, timeout and no progress cancel or block the step. Stop must not cancel a later unrelated request.

### 3. Sequential Scene runner and contact-kick adapter

- One in-memory run per Scene session. Capture Project/module, Scenario ID, Simulation ID/revision, exact actor/ball marker bindings and a run generation at start; recheck current availability before every dispatch.
- Subscribe before issuing each request. Use unique request IDs and process only exact matching responses. Deduplicate events; reject stale/different-Project/generation replies.
- Start Kick only after confirmed navigation arrival. Resolve the current semantic foot-kick mapping and loaded animation/contact-point availability; do not hardcode an FBX filename or directly drive an animation mixer.
- Reuse `THREED_SOCCER_KICK_REQUEST_EVENT` with contact timing and eligible foot points. Only the ball owner's correlated result can certify an applied kick. A completed clip after a miss never receives a substitute impulse.
- Stop cancels further dispatch and matching pending navigation/kick work, clears timers/listeners and invalidates replies. Preserve the ball owner's placement-before-impulse priority and one-impulse limit.
- Do not automatically restart on rendering, restored view state, Scenario load, definition save or a background settings change.

### 4. Scenario/Simulation UX and run notes

- Reuse Project Scene Blueprint/shadcn controls, accessible icon actions, title help, compact status and Toast feedback. Keep run control and results associated with the currently loaded Scenario/Project.
- Show explicit preflight reasons for unavailable actor, Scenario, target, module, rig/action mapping or simulation capability. Scope Run to an authenticated Project editor; public viewers cannot execute.
- Provide ready/running/completed/failed/cancelled/timed-out states, active step and bounded in-memory per-step outcomes. Store only allowlisted metadata; do not collect credentials or private Model metadata.
- If Sensor Group observations are included, capture baselines before dispatch and read scoped event/count deltas without resetting shared counters. Time-window sensor activity is an observation, not proof that a particular Action caused it. Observations lacking reliable correlation must be labelled accordingly.
- Run-result persistence, broader Action execution, general metadata collectors and cross-Project reuse remain later scope. No MQTT, worker or physical-device behavior is added.
