# v0.20.4 — ThreeD Scene: Scenarios

Status: roadmap checkpoint. This follows the released v0.20.3 — ThreeD Scene: Model Library + Physics Sensor Workflows. Package version and implementation scope remain unassigned.

## Purpose

A **ThreeD Scenario** is a Project-scoped arrangement of existing Scene Models, Physics Sensor Cuboids, Sensor Groups, and presentation rules that demonstrates a real workflow. Soccer and Farming are the first reference scenarios.

The Scenario layer explains what the Scene represents. It does not replace Runtime Marker ownership, Rapier physics, Sensor Group storage, ThreeD Layers, or the existing Model Library.

## Classification

| Area | Responsibility | First reference |
| --- | --- | --- |
| ThreeD Physics | Collision, sensor events, trigger/counter observation, transforms | A movable ball entering a sensor |
| ThreeD Soccer | A Scenario that arranges a pitch, balls, sensors, groups, and local match presentation | Home/Away named user metadata |
| ThreeD Farming | A Scenario that arranges Beds, Plantings, FarmBots, environment Models, and read-only observations | Garden/farm workspace |
| ThreeD Scenarios | Project-local setup, guidance, validation, and presentation over existing primitives | Soccer and Farming |

## Initial boundaries

- Scenario names and descriptions are metadata; they do not create special Physics record types.
- “Home,” “Away,” “Goal,” and “Score” remain Soccer metadata and presentation terms, never generic sensor field names or Physics API requirements.
- Scenarios may guide a User to create or connect existing assets. They must not silently create, move, persist, or delete Project assets.
- Local Scenario state must remain separate from persisted Project configuration and from external live-equipment observations.
- FarmBot remains read-only unless a future, separately approved command phase authorizes more.
- No schema work, external service, MQTT publish, or physical-device action is authorized by this roadmap entry.

## Candidate stable checkpoints

### v0.20.4.1 — Scenario contract and eligibility

- **Proof:** Inventory the Project assets and existing generic Physics/Sensor Group capabilities required by Soccer and Farming.
- **Act:** Define a bounded Scenario descriptor and eligibility evaluator using stable marker identities and current metadata.
- **Validate:** Unit validation confirms incomplete Scenarios are reported without mutation and that identical asset IDs across modules remain distinct.
- **Resolution:** A Scenario can describe readiness without owning the Scene.

### v0.20.4.2 — Soccer reference scenario

- **Proof:** A Soccer Project currently relies on manual knowledge of which Models and Sensors form the pitch and scoring locations.
- **Act:** Present a Soccer setup/checklist based on assigned assets and generic counter sensors. Keep user-selected Sensor Group names and sensor behaviors authoritative.
- **Validate:** Browser acceptance covers setup status, sensor entry counts, reset behavior, refresh, and no change to generic Physics functionality.
- **Resolution:** Soccer becomes a documented reference Scenario rather than a Physics-only special case.

### v0.20.4.3 — Farming reference scenario

- **Proof:** Farming assets are individually placeable but lack a shared Scenario-level explanation of their relationship.
- **Act:** Present a Farming setup/checklist using existing Beds, Plantings, FarmBots, environment Models, and read-only live-state conditions.
- **Validate:** Browser acceptance covers missing/available assets, saved positions, and stale/unavailable live observations without creating device commands.
- **Resolution:** Farming becomes a second reference Scenario while preserving the current operational boundary.

### v0.20.4.4 — Scene guidance and presentation

- **Proof:** Scene setup requires context without reintroducing overloaded DetailsCards or competing overlays.
- **Act:** Add optional Scenario guidance through the Project Toolbar/Project Tour and compact read-only Scene presentation. Preserve Project Assets, focused inspectors, and optional Sensors panel responsibilities.
- **Validate:** Verify one toolbar dropdown at a time, Project Assets persistence, narrow-screen access, persistent Canvas/Rapier lifecycle, and no camera change from passive selection.
- **Resolution:** Scenarios improve orientation without changing the underlying Scene controls.
