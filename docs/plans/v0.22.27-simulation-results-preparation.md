## Results lifecycle and developer decisions

`POST /api/threed/simulation-results` captures a saved active definition and revision, plus Project/module/Scenario labels, before Scene dispatch. An owner/run UUID identifies one attempt. Repeated capture resolves the same record; changed bindings/revision reject execution. Capture failure blocks movement. An ambiguous network response is resolved using that same UUID.

`PATCH` finalizes one run with `completed`, `failed`, `cancelled` or `timed-out`. The API validates ordered, correlated outcomes against the captured definition, not a subsequently edited definition. Identical final reports are idempotent; different replacement reports return a conflict. JSONB key order does not affect that comparison. Project/account/module deletion cascades history; Simulation/Scenario deletion unlinks their foreign keys while retaining snapshot identities and names.

Reports identify their source as `browser-scene`. They include client timings, per-step replies and selected Sensor baseline/final readings, group deltas, event totals, reset observations and truncation flags. Limits are 50 outcomes, 32 observation groups, 128 individual readings and 256 aggregate events. Definitions retain the 64 KiB limit; result bodies allow 256 KiB for those bounded named readings. Smaller saves use browser keepalive; larger saves use ordinary requests because browsers cap keepalive payloads. Trigger readings use zero counters; their activity contributes to group event totals. These observations do not certify a goal or establish causality.

The journal preserves unsaved reports across panel/Project navigation in the current page session, with a visible Retry control and a 20-entry unsaved limit. Retry only saves the original record/report. A hard close or crash can leave a `running` row with no final report; it means an unfinished report, not a confirmed active or completed simulation. No background executor, browser-storage queue or fabricated terminal state is introduced.

Shared Soccer choices update only `runToTarget`/`kickBall` steps; other Actions retain their own bindings and remain definition-only. Specific Sensor references are optional (up to 32 per group, 128 total); existing group-wide definitions remain valid. Missing selections remain visible. Advanced Character editors stay mounted behind the presentation toggle to retain drafts; explicit movement/Sensor editing remains available. Debug presentation does not disable physical colliders, event collection or scoring.
