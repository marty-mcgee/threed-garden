## Recommended milestone

Make the existing application foundation reliable and verifiable through **three bounded repairs**: remove an unused dependency that makes the graphics peer graph inconsistent; prevent optional browser preference storage from breaking the root theme provider; and release the procedural textures owned by the persistent Scene. Document the existing responsibility map and cover these repairs in the established validation dispatcher.

Concrete benefits: an internally compatible active dependency graph without framework upgrades; usable theme controls and provider initialization when browser persistence fails; and explicit GPU-resource cleanup while the active Scene remains mounted. “Top level” means these responsibilities agree across the app. It does not mean moving source into the repository root or introducing another application/Scene framework.

## Approved implementation sequence

### 1. Preserve and make the dependency baseline executable

Recheck dirty-worktree ownership, the absence of postprocessing consumers and actual lock metadata. Remove only `@react-three/postprocessing` and dependencies that become unreachable solely because of that removal. Regenerate/reconcile the lock with the declared npm version and review it for unrelated version movement. Do not change retained dependency versions or install broad updates. Keep the current root scripts/configuration conventions.

Add an offline `application-foundations` check to the existing dispatcher. Check root/lock consistency, installed active-stack resolution and declared peer compatibility using installed tooling. Cover deliberately mismatched metadata in fixtures so the check demonstrates it catches the audited failure. Limit singleton checks to the main application entry points; do not reject harmless nested type/helper packages merely for existing. Add no new runtime abstraction or runtime dependency for this validation.

### 2. Make theme persistence optional

Change only the existing ThemeProvider's persistence handling. Use the server-provided initial theme when browser reads fail; honor valid current/legacy saved preferences when reads succeed. Treat localStorage reads, localStorage writes and cookie writes as independent best-effort operations. A rejected persistence operation must not stop in-memory theme selection, DOM theme application, system-color synchronization or listener registration/cleanup. Preserve account-theme precedence and the existing storage keys/cookie semantics. Do not change session/auth providers, create a new settings service or redesign the theme UI.

Add actual-provider offline tests for throwing storage getters/getItem/setItem and cookie writes, invalid preferences, legacy migration, light/dark/system, media-query changes and listener cleanup. Preserve the existing WorkspaceSettings and panel-appearance tests.

### 3. Close the two procedural texture lifecycles

Within `ThreeDScene.tsx`, explicitly own acquisition/release of the procedural daylight background and grass textures. Each superseded texture must be released when replaced; the last owned texture must be released when its component exits. Background cleanup must only detach its own currently assigned texture and must not overwrite a successor. Setup/cleanup replay must leave a usable active texture rather than reuse a disposed resource.

Keep the current pixel generation, colors, texture repeat, lighting and ground dimensions. Do not dispose shared `useTexture`/Drei assets, imported Model geometry/material caches or the DRACO pool. Do not introduce a global resource manager or move components solely for organization. No Canvas/Physics remount, custom frame loop, new physics write, or change to collisions/stepping is permitted.

Add a focused `threed-scene-resources` offline fixture that executes the actual component resource lifecycles with mocked React scheduling and real Three.js texture-disposal events. Cover replacement, unmount, rapid environment/size changes, setup/cleanup replay, previous/successor background protection and shared-resource non-disposal. Use this fixture for ownership proof; do not require exact total GPU counts to be zero because renderer caches have their own lifetimes.

### 4. Document, validate and prepare the local checkpoint

Update existing architecture/index/validation documentation with the responsibility map, verified dependency policy and narrow resource ownership. Correct the specific stale current-release/debug statements without rewriting historical plans. Use the repository's normal `0.22.18` root package/lock version update only during the approved implementation. Update AGENTS.md, CONTEXT.md and this plan to distinguish implementation/local checks, pending Developer browser verification and any later release report.

Register `application-foundations`, `theme-provider` and `threed-scene-resources` in the existing CI group. Run the validation ladder below, review the entire diff, preserve unrelated Developer changes and leave all edits unstaged. One approval covers these routine stages and correction of failures within this scope. A finding that requires different behavior, new dependencies, schema work or a wider redesign must be reported separately rather than folded in.
