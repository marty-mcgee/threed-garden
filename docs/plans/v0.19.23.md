# v0.19.23 — ThreeD Audio

User-designated title and scope. Production remains v0.19.22; package version stays unchanged until release preparation. The local Audio workspace now creates speech; the earlier duplicate Track browser was superseded. The prior Help prototype was reverted and is excluded from this milestone.

## Product relationship

**ThreeD Music → ThreeD Audio**, using **ThreeD Models → ThreeD Model Files** as the relationship and workspace blueprint.

ThreeD Music is the parent context. ThreeD Audio is its file-focused sub-module: users work with real audio files, their settings, playback previews and saved state. It is not a separate top-level Help or AI product. Exact mapping to existing Music, Album and Track records must be established from implementation before selecting foreign keys or routes.

## Intended scope

- A parent Music selection and an Audio workspace that makes the current relationship explicit.
- Upload, inspect, preview and manage saved audio files using existing Music ownership and playback contracts where compatible.
- Fish Audio text-to-speech and speech creation within that workspace: source text and voice/settings, explicit generation, playback preview, and saving generated audio as a related asset.
- Compact controls and progressive disclosure following the accepted Model Files layout. Distinguish temporary generation/preview from successfully saved files.

## Development sequence

1. Inspect Music schema, CRUD, upload, stream and deletion paths. Document the concrete parent/child mapping and file storage contract; do not infer that a Music Track is equivalent to a parent Music record.
2. Design the Audio workspace around that mapping, including empty/loading/error states and file ownership. Present any required schema additions for approval before implementation; live database changes remain separate.
3. Implement the smallest file-management and playback checkpoint using existing contracts, then validate it locally.
4. Add a server-only Fish Audio adapter and bounded generation lifecycle. Explicit generation, provider failure handling, duplicate-request protection and saved-file cleanup must precede live use.
5. Validate upload, playback, generation, save/reload and deletion; prepare release only after acceptance and the user's manual build.

## Boundaries

Help redesign, visual tours, tutorial narration, Character dialogue and Scene audio assignment are deferred. No new header Help controls. No credential edits, paid API requests, schema changes, Git commits, pushes or deployments are authorized by this planning update.

The earlier [Help + AI Audio exploration](threed-help-ai-audio-foundation.md) is historical; this plan supersedes its milestone scope.

## First development checkpoint

Inspection confirmed the existing file relationship is Albums → Tracks: Tracks store `albumId`, `fileUrl`, and `fileType`. A direct Music-record → Album relationship has not been established. This checkpoint reuses the existing owner-scoped Album and Track APIs without adding schema or inventing a new relationship.

Implemented `/admin/music/audio`, reachable through **Admin → Music → Audio**. Users select an album, select one of its Tracks, and explicitly start a native audio preview. Album choices are paginated; requests are cancelled when selections change. Loading, empty, request-error, and playback-error states are displayed.

Preview accepts saved HTTP(S) or local absolute-path URLs. Storage keys are shown as requiring a playable URL. The existing stream endpoint can substitute sample audio when storage is unavailable, so this workspace does not use it. Verified storage-key playback must be addressed before expanding file management. Uploads, generation, and deletion are not implemented in this checkpoint; Manage Tracks links to the existing editor.

Validation: `npm run typecheck` and `git diff --check` passed. Browser playback remains a manual check; no production build, schema change, provider request, commit, or deployment performed.

Manual review: open Admin → Music → Audio, select an album and a Track with a known audio URL, then press Play. Confirm the selected file plays. Also review an empty album and a Track whose file reference is a storage key: neither should play substitute sample audio.

## Second development checkpoint — saved audio preview resolution

The first workspace could only play direct URLs. Inspection of the legacy stream endpoint confirmed sample-audio fallback and play-count writes, so it is unsuitable for an editing preview.

Added `GET /api/music/tracks/[trackId]/preview`, with authentication and a Track-owner predicate matching the existing owner Track list. It resolves the saved HTTP(S)/local asset URL or signs an existing storage key through the Music storage service. Responses are private/no-store. Missing files, unsupported references, unconfigured storage and signing failures return errors; preview does not substitute audio or update play counts. Local API references are rejected. No changes were made to the legacy stream endpoint.

The Audio page requests resolution when a Track is selected, aborts obsolete requests, and displays preparation/error states. Playback remains user initiated. This supersedes the first checkpoint's storage-key limitation, subject to existing server storage configuration. Signing a reference does not prove that its object exists; missing objects and unsupported formats remain browser playback errors. No live storage request was made during development.

Validation: `node src/lib/scripts/validate-music-audio-preview.cjs`, `npm run typecheck`, and `git diff --check` passed. Fixtures execute the actual handler with mocked auth/query/storage, covering unauthenticated access, owner query predicates, invalid IDs, empty/unsupported references, direct/local URLs, missing configuration, signing and sanitized failures. They do not prove live file playback.

Manual review: **Admin → Music → Audio**, choose an album and Track, then press Play. Check a direct file URL and, if already configured, an existing storage-backed Track. Missing configuration should show an explicit message, not a sample song. Switching Tracks should replace the preview and stop the prior player. Upload and Fish Audio generation remain subsequent stages. Existing planning and sidebar work is retained; no version bump, schema change, environment edit, commit or deployment.


## Corrected scope — Fish Audio speech creation

User clarified that Tracks already owns audio file management. Audio is the speech-creation workspace, not another Album/Track browser. The earlier read-only browser and its dedicated preview endpoint/fixture were removed. Existing Music playback and Track CRUD remain unchanged.

Implemented text and voice-ID input, explicit Generate speech, temporary preview and MP3 download at `/admin/music/audio`. A generated preview retains its text/voice snapshot and indicates when inputs have changed. Object URLs are revoked on replacement/unmount, and requests are aborted on departure. Generation is guarded against duplicate clicks within the workspace.

The authenticated `/api/music/audio/generate` endpoint uses a server-only `FISH_AUDIO_API_KEY` (configuration name only; no environment file edited). GET reports configuration presence, not provider health. POST validates up to 2,000 text characters and a 32-character hexadecimal voice reference; uses the documented `s2-pro` MP3 request, a 45-second timeout and 10 MiB response ceiling. No automatic retries, database writes or provider error-body logging. Account-wide/distributed request deduplication is not implemented.

Official contract checked: https://docs.fish.audio/api-reference/endpoint/openapi-v1/text-to-speech . Voice browsing is available through Fish Audio. No live provider request or credit expenditure occurred during development.

Persistence handoff remains pending: this checkout's Track CRUD accepts an audio URL, and an existing upload handler has not yet been located. Do not claim Download MP3 saves a Track. Locate the user's current upload workflow before implementing Save as Track; reuse its storage/registration path.

Validation: `node src/lib/scripts/validate-music-speech.cjs`, `npm run typecheck`, and `git diff --check` passed. The new fixture mocks the provider and checks authentication, input validation, missing configuration, request format, MP3 response and sanitized provider failures. Browser and live provider validation remain outstanding. No build, commit, schema changes or deployment.

## Multimedia direction and Track upload checkpoint

User accepted Multimedia as the proposed broader module: Audio Library, Speech Studio, Music Albums/Tracks, and future Video. Speech Studio stays with Multimedia; ThreeD may reference its assets later. Rename/navigation restructuring is deferred until file workflows are accepted. No schema additions are approved or introduced.

Implemented a file option in Tracks → Add Track, using the existing POST `/api/music/tracks` registration contract. Multipart requests accept MP3/WAV up to 4 MiB, check extension/header signatures and server-derived MIME/size, verify Album ownership, then upload to the existing public Vercel Blob store at `music/users/{encodedUserId}/audio/{uuid}.{extension}`. Registration stores the returned URL in the existing Track. Database failure triggers best-effort deletion of that newly uploaded Blob. A process termination or failed cleanup can still leave an orphan; no claim of a distributed transaction is made. Existing JSON URL registration remains available.

The UI uploads only on Create Track, disables URL entry when a file is selected, fills an empty title from the filename, and clears the fabricated default duration for file uploads. Duration can be entered manually; it is not measured automatically. Public URL access is disclosed beside the file chooser. Existing Track deletion remains record-only and does not delete its Blob; safe reference-aware file deletion is a later lifecycle step.

This bounded server-upload checkpoint follows https://vercel.com/docs/vercel-blob/server-upload (4.5 MB request body limit). Larger audio requires direct client uploads in a later step. No credentials or environment files were accessed/changed. Existing Blob configuration is reused.

Actual POST handler fixtures mock database and Blob operations and cover auth, Album ownership, invalid/oversized files, MP3/WAV types, registration, cleanup and existing JSON URL creation. No real uploads, Fish calls, build, commits or deployment performed. Earlier Audio/sidebar/planning work is preserved.

## Generated speech → S3 → Track

Added a Save as Track section below generated speech. It loads owner Albums with pagination, takes a Track title, uploads the captured MP3 through the existing S3 start/PUT/complete contract, then invokes the existing Track POST. Stored lyrics and metadata describe the actual generated preview (source, voice ID, model), not subsequently edited inputs. Generation is disabled during saving. A verified file reference survives a registration retry within the mounted component. A synchronous request ref prevents duplicate clicks; successful save disables repeated registration. An ambiguous registration response disables retry and directs the user to inspect Tracks. This is not durable/server-side idempotency.

Existing S3 limits/lifecycle apply, including possible abandoned uploads and private owner playback. Download remains available independently. No schema/API route additions, live generation, S3 upload, environment edits, commits or deployment were performed for this step.

Validation passed: `node src/lib/scripts/validate-music-speech-save.cjs` (actual extracted save handler with mocked requests), `node src/lib/scripts/validate-music-s3.cjs`, `node src/lib/scripts/validate-music-speech.cjs`, `npm run typecheck`, `git diff --check`. ## Fish Audio failure diagnostics

User supplied a generation request and the generic failure response. That response did not retain the provider status, so authentication, balance, voice access and validation failures could not be distinguished. The handler now returns `providerStatus` and a bounded status-specific message (400/401/402/403/404/422/429, generic otherwise). Raw provider bodies, credentials and submitted speech are not included in diagnostics. The UI displays the error in red. Request mapping remains `voiceId` → `reference_id` as documented at https://docs.fish.audio/api-reference/endpoint/openapi-v1/text-to-speech .

Speech fixtures now verify status reporting and omission of raw error bodies; fixtures, TypeScript and diff checks passed. No live generation or environment access. Root cause remains unconfirmed until the user retries and obtains the provider HTTP status.

## Free Fish Audio model

User reported provider HTTP 402 and requested `s2.1-pro-free`. The earlier integration hard-coded `s2-pro`. Fish Audio's current official developer examples and free-model announcement document changing the model header to `s2.1-pro-free` with the same reference_id request. Switched generation and newly saved Track metadata to that identifier; the UI displays the model instead of the paid-credit message. No paid-model fallback. Sources: https://fish.audio/developers/ and https://fish.audio/ar/blog/s2-1-pro-free-api/?articleLocale=en . Free access remains subject to provider account/fair-use terms.

Speech generation/save fixtures explicitly assert the free model; both fixtures, TypeScript and diff checks passed. Live generation remains user verification; no credentials changed or provider requests made by the agent. Refresh the Audio page and generate a new preview before saving.
