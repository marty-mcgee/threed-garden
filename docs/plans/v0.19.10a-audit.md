# v0.19.10a Stage 1 — FBX bulk-import audit

Completed September 9, 2026. This is a repository audit with offline checks, not a live upload or browser verification. The worktree was clean at the start. No application, schema, or storage behavior changed.

## Existing paths

| Area | Working single-Model path | Existing bulk component |
|---|---|---|
| Entry | `ThreeDModelsCRUD.tsx` opens Import New Model | `ThreeDModelsBulkImport.tsx` exists, but no source consumer imports or renders it |
| Primary upload | Authenticated `/api/threed/models/upload`; FBX structural analysis before Blob storage | Same endpoint, but retains only URL, size, and type; discards returned analysis |
| Review | Shared editor and live `ThreeDModelAssetPreview`; scale, rotation, offsets and configuration | Name and scale per item, optional thumbnail image, shared categories and flags; no live Model preview |
| Creation | `/api/threed/models` receives `primaryFile`; transaction creates Model and primary file record, sets `mainModelFileId` | Sends URL on Model only; omits `primaryFile` |
| Textures | Post-creation Model Files workspace, dependency inspection, attachment resolver, reusable Texture selection and material assignment | Per-row companion selection and attachment uploads; no reusable Texture or material assignment controls |
| Completion | Existing Model and Model Files management | Sequential upload → inactive Model → attachments → active-status PATCH; per-item success/failure |

The single importer also stages the primary before Model creation; supportive textures are managed after creation. Bulk import should reuse that lifecycle rather than assume the single importer already stages complete bundles.

## Confirmed gaps and consequences

### 1. Bulk UI is deliberately disconnected

Repository search finds `ThreeDModelsBulkImport` only in its own file. The Model administration guide explicitly documents its removal from the primary surface. Restoring a button alone would expose the contract mismatches below.

Affected files: `src/components/admin/threed/models/ThreeDModelsCRUD.tsx`, `ThreeDModelsBulkImport.tsx` in the same directory; `docs/developers/THREED_MODEL_ADMIN.md`.

### 2. Primary-file registration is missing

Bulk creation omits `primaryFile`; the Model POST route only creates the authoritative primary attachment when that payload is supplied. A newly bulk-created Model therefore has no primary Model Files row or `mainModelFileId`. The dependency GET route searches file records and reports `missing_primary`, even though the Model has a runtime URL. Rendering may still use that URL; missing registration does not prove all rendering fails.

Affected files: bulk component; `src/app/api/threed/models/route.ts`; `src/app/api/threed/models/files/requirements/route.ts`.

### 3. Attachment preparation contradicts the current API and resolver

The bulk component defaults attachments to the discovered reference or bare filename. Its path check allows bare filenames and does not enforce the API's 100-character directory limit. The files POST route requires a directory. Bulk readiness uses exact relative-path matching; the Model Files audit and runtime allow an unambiguous filename fallback.

Offline reproduction: a discovered `Barn_Wall.png` is considered satisfied by that bare path, which lacks the API-required directory. Changing the selected path to `textures/Barn_Wall.png` makes bulk readiness fail. The released single-Model path supports this directory arrangement.

Affected files: bulk component; `src/lib/services/threed/models/model-companion-core.ts`; `model-attachment-runtime-core.ts` in the same directory; `src/app/api/threed/models/files/route.ts`.

### 4. Batch preparation and configuration lag behind single import

There is no shared texture pool, folder selection, batch dependency matching, or per-Model material-target review. Each row selects its own companions. File identity uses name, size, and last-modified time, excluding relative path; distinct same-named files can collide. All primary files are read concurrently for inspection, up to a 100-item queue, without a client size or aggregate-memory preflight.

The FBX companion scanner searches decoded bytes for image filenames; it does not establish valid FBX structure or complete dependency discovery. An offline check confirms arbitrary text named `.fbx` returns zero requirements. The server still performs structural analysis before storage, so this is misleading client readiness rather than a server validation bypass. Embedded-texture and binary-FBX accuracy need representative assets before stronger claims.

Bulk's ready count also excludes name/scale validation, although Import checks those fields. A single invalid eligible item blocks all eligible imports. Bulk permits a positive scale below the single editor's `0.01` minimum.

Affected files: bulk component; companion core; `src/components/admin/threed/models/model-admin-form-core.ts`; `ThreeDModelEditorFields.tsx`, `ThreeDModelAssetPreview.tsx`, and `ThreeDModelFilesCRUD.tsx` in the same directory.

### 5. Retry support is limited to retained browser state

The queue remembers returned upload URLs, Model IDs, and successful companion identities, and skips created items on retry. However:

- Once a Model ID exists, row fields and companion controls lock, even after attachment failure. Users cannot correct the failing path or replace that file in the queue.
- Refresh or Clear Queue discards progress; there is no durable batch resume or result report. Closing the dialog alone preserves state while the component remains mounted.
- If a create or attachment commits but its response is lost, the client lacks reconciliation: retry may duplicate a Model or meet the attachment API's duplicate-path rejection.
- Clear Queue does not clean staged uploads. Changing a preview after a failed attempt does not invalidate a cached thumbnail URL.
- Finalization sets status to `active` after requests succeed, without reloading dependency or configuration readiness. “Created” is not proof that materials render correctly.

These are code-path findings; network-failure behavior has not been exercised against production.

Affected files: bulk component; upload, Model, and files API routes. Keep recovery changes scoped to this path; do not infer authorization for a new persistence system.

## Separate CLI path

`src/lib/scripts/import-threed-models.ts` consumes a manifest and requires explicit `--apply`, owner ID, and report arguments. It writes through its own database/Blob workflow and matches existing Models by owner and `metadata.importKey`. It is not the Admin bulk component's backend.

It also does not register a primary file row, and supporting-file writes omit the dedicated `relativePath` field while retaining source paths in metadata. Its 500 MB primary file-plan limit differs from the upload API's 256 MB limit. These are separate compatibility issues; do not route browser imports through this script or change it as part of restoring the Admin workflow. The script was inspected, not executed.

## Proposed Stage 2 — define FBX batch preparation

Start with a reviewable preparation contract before exposing bulk creation:

1. Identify each FBX independently and show consistent name, scale, file-size, and inspection states. Invalid items must explain what needs attention.
2. Separate source references from valid Model-owned attachment destinations. Reuse exact-path/unique-filename resolution; ambiguous filenames require an explicit choice.
3. Define shared texture selection and per-Model association. Keep filename dependencies distinct from explicit material-target assignments, using the existing Texture workflow where applicable.
4. Define shared defaults versus per-Model overrides and the handoff to existing Model Files configuration. An imported Model must have a discoverable review/repair destination.
5. Specify whether to import only ready items or require the whole batch to be ready. The count, button, and validation must agree.

Before Stage 3 exposes writes, acceptance must include transactional primary registration, valid attachment destinations, correction of failed items, and explicit handling of uncertain request outcomes. A retry must preserve known successful work. No new schema is required by this audit.
