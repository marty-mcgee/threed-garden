# v0.22.11 — ThreeD Physics Improvements and Testing in Multiple Projects and Environments

**Planning draft; title tentative.** v0.22.10 is User-confirmed in production. The next test starts with a new Project rather than changing Project 15. The Soccer Field is a regular **Scene Object** Model within a larger Scene that uses an Environment preset and **Procedural** Ground Map. The field is not the Project's Environment / Base Map. No new Project, asset assignment, database row, or physics change has been made by this plan.

## Problem and current implementation

The released playable Soccer path was exercised in Project 15 with the field assigned the Environment / Base Map role. That role hides procedural grass, defaults to fixed triangle-surface collision, and can use Environment-specific collision regions. It therefore cannot establish that a normal field Model works on a separate ground collider, or that ball, Character, goal Sensors, camera, and saved state behave consistently when the same assets are used in another Project.

The existing Scene already renders a procedural ground with a fixed Rapier collider, or an optional larger ground plane. A regular Model can request **Fixed Triangle Surface** in its DetailsCard; its fallback is a whole-Model box when a usable surface is unavailable. The field's goal Sensors belong to its Project Model instance, and the built-in **Use as Action Target** choice belongs to the ball Model instance. Generic Physics Sensors own counts. A Setup Guide readiness check is an inventory check, not proof that a ball can cross a goal.

Relevant code paths for the first implementation step: `src/components/map/ThreeDScene.tsx` (`ProjectModelMarkerBody`, procedural ground, ball body, and Sensors), `src/libraries/services/threed/models/project-model-instance-core.ts` (role and collision policy), `src/components/map/details/ModelInstancePlacementEditor.tsx` (Scene Role and Physics Mode), and the Project view-state and Sensor services already exercised by v0.22.10. Inspect the current files again before editing.

## Rapier and Ecctrl first

The installed libraries are `@react-three/rapier` 2.2.0 and `ecctrl` 2.0.0. Use their existing simulation and movement facilities before adding custom motion code:

- **Surfaces and ball:** keep fixed Rapier bodies for procedural ground and field geometry, and the existing dynamic `BallCollider` body for the ball. Inspect actual `TrimeshCollider`/box fallback shapes with Rapier debug rendering. Test gravity, collider mass, friction, restitution, damping, continuous collision detection, sleeping/waking, and `applyImpulse` through the existing Rapier owner. Prefer tuning those supported properties to manually changing ball translation or velocity each frame. [React Three Rapier guide](https://github.com/pmndrs/react-three-rapier#readme); [Rapier rigid-body API](https://pmndrs.github.io/react-three-rapier/classes/RapierRigidBody.html).
- **Goals:** keep Rapier sensor colliders and their intersection enter/exit events as the source of overlap observations. The app's generic Sensor service should still own direction filtering, deduplication, persistence, and counts. A sensor detects passage without exerting a contact force. [React Three Rapier sensors](https://github.com/pmndrs/react-three-rapier#sensors).
- **Character:** keep Ecctrl's capsule, support/ground detection, movement, jump, slope handling, balance, and normal camera-relative input in `EcctrlCharacter`. Inspect its exposed mass, movement, spring/damping, balance, and counter-impulse settings before changing app-specific WASD or contact code. Retain the current animation-completion handoff for a deliberate kick; Ecctrl locomotion and Rapier contact should handle ordinary movement. [Ecctrl API reference](https://github.com/pmndrs/ecctrl/blob/main/docs/api-reference.md).

Record the installed-version behavior during testing; current upstream documentation describes available concepts but is not proof that a particular prop or default behaves identically in these pinned packages. Preserve the established App wrappers and Character action path rather than bypassing them.

## Target setup

1. Create a fresh, owner-scoped Project with its own ThreeD module and a larger procedural ground. Record the Project ID and relevant stable marker IDs in test notes after creation; do not hard-code them into the app. Leave Project 15 as the released comparison case.
2. Assign the reusable Soccer Field as a **Scene Object** and request **Fixed Triangle Surface**. Place its visible pitch at the intended ground height and verify the active collider with Physics Debug. Use an Environment preset for the surrounding scene; the field must not be flagged as Environment / Base Map merely to obtain collision.
3. Add one movable ball and one eligible movable Character. Select that exact ball through **Use as Action Target**. Attach or configure a named Score Sensor on the new field instance, with explicit direction and Sensor Group. Add a Protect Sensor only when its purpose and placement are clear. Save the Project and, if desired, save a Project-scoped Soccer Scenario setup using those new Project assets.
4. Record a controlled baseline: ground/field seam, ball rest and rolling, kick impulse, Character contact and WASD, goal entry direction, exit/re-entry, Save/reload, Project switching, Layer visibility, and camera focus. Compare with Project 15 without copying its counters or instance metadata into the new Project.

## Boundaries and open measurements

This plan does not authorize a schema migration, automatic Project provisioning, reusable Model mutation, a new Soccer scoring engine, FarmBot behavior, or production deployment. Project setup is deliberate work in the new Project. Keep the persistent Canvas/Rapier world, stable marker identity, Project ownership, separate Garden/Ecctrl Character paths, and generic Sensor count authority. Preserve v0.22.10's built-in Model target flow and post-animation kick impulse.

Before choosing code changes, measure whether the field's imported geometry yields a usable fixed triangle surface as a regular Model, whether its generated collider includes any unwanted underside or goal obstruction, and whether ground and pitch heights overlap or leave a step. Test with the procedural ground alone, then with the placed field; do not infer a collision result from a visual screenshot. Browser acceptance should include one clean kick goal, a second goal after exit/re-entry, a rejected reverse crossing, smooth WASD after repositioning, and Save/reload in the new Project. The exact tuning values and any UI additions remain undecided until those observations exist.
