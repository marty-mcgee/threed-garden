# v0.19.40 — Admin Settings: Personal Workspace Preferences

Status: Released to production; deployment User-confirmed. Package `0.19.40`. No schema change was required.

## Goal

Improve `/admin/settings` using the compact ThreeD Admin Blueprint. Every editable setting must have an identified App consumer, truthful scope, validated persistence and observable behavior after Save and reload. Use the existing route (`src/app/admin/settings/page.tsx`); `/page` is not part of its public URL.

## Prove — current implementation

- `src/app/admin/settings/page.tsx` reads bundled settings and exposes a server Save action without its own authentication, authorization or input validation.
- `src/components/admin/settings/SettingsManager.tsx` exposes module, service and feature switches with no dirty baseline or discard action. Switches need associated accessible labels, descriptive names and compact, consistent layout.
- `src/lib/config/settings.ts` writes to `lib/config/settings.json`, although the actual file is `src/lib/config/settings.json`. Writing a deployment-local file also does not provide durable shared persistence. The active Save flow does not use the database.
- `src/lib/config/settings.client.ts` imports bundled JSON. `src/components/navigation/NavDropdown.tsx` builds navigation once on mount through `src/lib/config/navigation.client.ts`; saved changes cannot reach it through this path.
- The navigation builder consumes module flags and selected service flags. Searches found no consumers for the advertised polling, cron, dashboard and API-documentation controls. Hiding a navigation link is not equivalent to stopping a service or denying route access.
- `src/components/admin/layout/AdminSidebar.tsx` has its own static navigation. Dashboard Home also renders its own module discovery controls and links.
- Unused database helpers in `settings.ts` select an active deployment without an environment constraint, merge arbitrary dotted keys and use one cache for all users. They must not become the new persistence path without correcting those boundaries.
- `src/lib/schema/settings/index.ts` already defines setting definitions, per-user overrides, deployment snapshots and audit records. No new schema is currently proposed. Existing definitions include sensitive integrations; a general settings-table response must not be sent to the browser.
- `src/app/admin/layout.tsx` requires a session on the client, but does not establish privileged administration. A global write requires a verified server authorization policy; a personal preference requires owner-scoped reads and writes.

## Ownership decision

Clarification requested: should editable Settings affect only the signed-in User's workspace, or the entire App through authorized administrators? This determines persistence ownership, visibility and write permission. Do not infer global-write permission from access to the Admin layout.

Following plan approval without a separate scope selection, this increment uses the conservative personal-workspace scope, stated to the User before implementation. It does not implement global administration. Concrete acceptance: Appearance applies through the existing theme provider; module navigation preferences affect the Admin sidebar, Dashboard quick links and Dashboard navigation menu; individual Dashboard menu links may be hidden. Projects and direct route access remain available. Save uses an authenticated owner-scoped override with conflict detection and transactional audit, replacing the page's filesystem action. Existing settings tables are reused. Unsupported execution controls are removed from this editable workspace. Changes target the Settings page/manager, a dedicated workspace contract/service/provider/API, the three navigation consumers, and the version plan.

Appearance follow-up proved during review: AdminLayout, AdminHeader, AdminSidebar and AdminFooter paint fixed dark backgrounds even when the existing theme provider selects Light. Make those shell backgrounds/borders theme-aware, retaining current dark-mode colors. This is required for the exposed Appearance control; it does not restructure the shell or change other routes' viewport sizing.

## Development stages

1. **Define supported settings.** Resolve ownership, inventory each proposed control's exact consumer and agree on what its label promises. Prefer a smaller working set over placeholder switches. Keep unsupported automation/integration controls out of the editable form until their actual execution paths are wired.
2. **Implement validated persistence.** Use existing schema where it fits the confirmed scope. Authenticate every server read/write, allowlist accepted fields, validate types and return only safe display settings. Avoid local-file writes, cross-user caches and silent success on failed saves. Preserve unrelated settings and credentials. If schema changes become necessary, request explicit approval first; the User's schema protocol remains `bun db:generate` and `bun db:push`.
3. **Apply saved values.** Connect each exposed setting to its proven consumer. Define initial loading, refresh, sign-out/account-switch behavior and failure recovery. Keep navigation preferences distinct from route authorization, background job execution and physical-device operations.
4. **Compact Settings workspace.** Use a compact toolbar, clear sections, accessible controls, dirty state, Save, Discard and explicit save/error feedback. Avoid persistent instructional clutter; explanations can live in an optional disclosure. Changes remain scoped to Settings and identified consumers, without global Admin layout restructuring.
5. **Validate and review.** Add targeted persistence/consumer checks where appropriate, run TypeScript and diff checks, then request browser review of Save → navigation → reload, failure recovery, account isolation, keyboard use and narrow screens. Prepare release documentation only after development and User review.

## Acceptance criteria

- Every enabled control changes the documented behavior and survives reload according to its stated persistence scope.
- Saved and unsaved state are distinguishable; failed saves retain drafts and never announce success.
- Session identity and any required administrator authorization are checked on the server. Malformed or unknown settings cannot be persisted through the UI endpoint.
- No cross-user preference leakage, credential exposure or mutation of shared imported defaults.
- Settings remain reachable even if optional navigation sections are hidden.
- Polling, cron and service labels do not claim effects that have not been implemented and validated.
- Compact desktop/mobile layout follows the existing Blueprint; labels and focus remain accessible.
- Existing Project state restoration, ThreeD runtimes and FarmBot safety boundaries remain unchanged.

## Implemented development checkpoint

- Replaced the filesystem-backed Settings page action with `/api/settings/workspace`. Both reads and writes authenticate the User. Writes also check request origin and strictly validate the versioned, allowlisted payload.
- Reused existing Settings tables with the dedicated `workspace.preferences.v1` definition and owner-specific override. Save locks the definition within a short transaction, verifies a revision token, upserts the override and records its audit entry atomically. No deployment snapshot or arbitrary setting key is exposed; no shared server cache is used. The legacy configuration helpers remain unused by this workspace.
- Added a shared account-aware client provider. Late responses from another account cannot replace current preferences. Successful saves update the three navigation consumers and the existing theme provider. Sign-out/account transitions discard the previous account's preferences. Existing Scene children remain mounted while preferences change.
- Added Appearance, Module Navigation and Dashboard Menu Links, with associated labels, compact Save/Discard/Refresh controls, dirty state, defaults-as-draft, failed-save retention and conflict feedback. Unsupported execution switches are absent. Help is an optional disclosure.
- Applied the compact viewport workspace only to Settings. Admin shell backgrounds/borders now support Light while preserving existing Dark colors. Direct routes, Projects, Scene state and physical-device behavior remain unchanged.
- Added [the user guide](../users/SETTINGS.md), a repeatable `validate:workspace-settings` command and its CI step.

### Automated validation

### Browser/database review before release

1. Open `/admin/settings`; confirm compact controls, loaded preferences and no runtime console errors.
2. Hide one module and a Dashboard menu link, Save, and verify sidebar/menu/quick-link changes. Reload and verify persistence. Confirm Project cards and direct URLs still work. Hide all modules and confirm Settings/Projects stay reachable; restore defaults and Save.
3. Save Dark, Light and Follow device in turn; inspect Settings and the surrounding shell. Test the header theme button, reload, and Use browser preference. Verify contrast and keyboard/touch operation on a narrow display.
4. Change a field, Discard, and confirm the saved value returns. Restore Defaults should remain unsaved until Save. Refresh must ask before discarding a dirty draft.
5. Open two Settings windows and load the same revision. Save one, then save the other; expect conflict feedback without overwriting. Refresh and retry deliberately.
6. Verify failed read/save feedback and retained drafts using browser request blocking. Check separate accounts do not share preferences. These are required live acceptance checks, not results inferred from offline tests.
7. Open a ThreeD Project and confirm navigation/Settings changes did not regress Project Save/restore or Scene control. The User retains the manual build and production release gate.
